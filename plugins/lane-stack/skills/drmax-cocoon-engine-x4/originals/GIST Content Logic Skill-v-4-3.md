## 0. Purpose

**GIST Content Logic v4.3** is a modular system for designing pages and content as decision-support tools.

It is not intended to:

- write as much text as possible;
- add formal SEO phrases without user value;
- create an appearance of expertise;
- make wording “unique” without adding new meaning;
- cite research merely to appear authoritative;
- cover a topic exhaustively at any cost;
- treat every page as requiring the same research and audit depth.

The primary objective of GIST is:

> Create a page that is difficult to replace with typical competitor content because it resolves real user uncertainties faster, more precisely, and with better evidence.

GIST maximizes:

- **Utility** — usefulness for the user’s decision;
- **Diversity** — semantic and decision-function variety;
- **Evidence** — support for important claims;
- **Actionability** — the ability to take a concrete next step;
- **Trust** — justified confidence;
- **Necessity** — the importance of the information to the page’s task;
- **Distinctiveness** — the degree to which the information is difficult to reproduce generically.

GIST minimizes:

- **Redundancy** — semantic repetition;
- **Replaceability** — how easily a generic competitor can reproduce a block;
- **Noise** — information that does not improve the decision;
- **Unsupported claims** — assertions without adequate support;
- **Decision friction** — obstacles that make choosing or acting harder.

## 1. Core GIST model

For every content block, ask:

1. What user uncertainty does it resolve?
2. What decision or action does it improve?
3. How is it different from the blocks already selected?
4. Why should the user trust the claim?
5. What would be lost if the block were removed?

A simplified model is:

$$
\text{Page Value}
=
\text{Utility}
+
\text{Diversity}
+
\text{Evidence}
+
\text{Actionability}
-
\text{Redundancy}
-
\text{Replaceability}
-
\text{Noise}
$$

This is a reasoning model, not a literal automated ranking formula.

### 1.1. Utility

Utility is a block’s contribution to the user’s actual task.

A useful block helps the user:

- choose;
- compare;
- reject an unsuitable option;
- assess risk;
- understand a limitation;
- take the next action;
- avoid a post-purchase mistake;
- assess suitability for a specific scenario;
- verify whether a claim applies to their situation.

The following are not sufficient reasons to include a block:

- “It is related to the topic.”
- “It sounds expert.”
- “It is not already on the page.”
- “It is generally useful.”
- “A competitor has something similar.”

### 1.2. Diversity

Diversity is not variety in wording or the number of subtopics. It is diversity in **decision functions**.

Two blocks are meaningfully different when they provide different:

- selection criteria;
- types of evidence;
- use cases;
- limitations;
- risks;
- verification methods;
- comparisons;
- actions.

A new formulation of the same point is not a new meaning.

### 1.3. Utility without diversity

High utility without diversity produces a cluster of repetitions:

- several similar recommendations;
- multiple versions of the same benefit;
- repetition of one argument across several sections;
- a long page that does not expand the user’s decision space.

### 1.4. Diversity without utility

Diversity without utility produces irrelevant novelty:

- unusual but unhelpful facts;
- secondary details;
- unrelated research;
- interesting observations that do not change the user’s decision;
- additional sections added only to make the page look comprehensive.

### 1.5. Replaceability

Replaceability is the likelihood that a competitor or language model could reproduce the same block in a few minutes.

High replaceability is typical of:

- generic definitions;
- obvious benefits;
- templated introductions;
- universal advice without context;
- unsupported promises;
- summaries of widely known information;
- wording that could be placed on almost any page.

Low replaceability comes from:

- a specific selection criterion;
- first-party data;
- a measurable filter;
- a scenario-specific limitation;
- local or operational information;
- a transparent comparison method;
- a real mechanism;
- evidence tied to a concrete decision;
- a proprietary method of verification.

### 1.6. The max-min intuition

When selecting a set of blocks, do not simply collect the most useful blocks independently. Avoid allowing the entire set to become a cluster of similar meanings.

Practical question:

> Which next block adds the most useful information while introducing the least repetition of meanings already selected?

## 2. The page as a decision system

A strong page often follows a chain like this:


User scenario
    → selection criterion
    → filter or exclusion
    → comparison
    → suitability check
    → evidence
    → next action


For a commercial category:


Purchase scenario
    → filter
    → comparison
    → size or measurement check
    → real reviews
    → product or bundle selection


For an informational page:


Question
    → cause or mechanism
    → possible solutions
    → limitation
    → selection criterion
    → result verification


For a comparison page:


User task
    → criteria
    → differences
    → who each option suits
    → limitations
    → final choice


The page does not have to follow this sequence literally, but the user should understand:

- what to choose;
- on what basis;
- what to check;
- when the recommendation stops applying;
- what action to take next.

## 3. Routing rule

GIST v4.3 is modular, but modularity must not weaken required checks.

Use the smallest module set that can reliably solve the user’s task. Escalate to additional modules when the page contains unresolved:

- factual uncertainty;
- research uncertainty;
- competitive uncertainty;
- transfer risk;
- measurement uncertainty;
- operational risk;
- high-consequence user decisions.

### 3.1. Standard routing


Basic content creation:
A + B + D + F + J1 + K

Page audit:
A + B + D + F + I1 + I4 + I5 + K

Research-based analysis:
A + B + C + D + G + H + I2 + K

Meta title and description:
A + B + E + I3 + K

Category-page optimization:
A + B + D + E + F + H + I1 + I4 + K

Full research-driven redesign:
A + B + C + D + E + F + G + H + I + J + K


### 3.2. Routing principles

1. Do not run the full research pipeline for a simple copy task.
2. Do not skip decision mapping merely because the task appears to be “SEO.”
3. Do not use the meta module as a substitute for page-level utility.
4. Do not use the research module unless research can change the page, the evidence, the measurement plan, or the decision.
5. Use the audit modules proportionally to the risk and complexity of the page.
6. When the user does not specify depth, choose the smallest reliable module set.
7. Escalate when the smallest set cannot resolve a meaningful uncertainty.

## 4. Ten signs of a strong page

A strong page:

1. **Starts with the user’s task**, not a generic introduction.
2. **Quickly explains who the page or offer is for and which scenarios it covers.**
3. **Provides selection criteria**, not merely a list of benefits.
4. **Includes filters and exclusions** that help users reject unsuitable options.
5. **Distinguishes similar options** using attributes that affect the decision.
6. **Uses specific and verifiable facts.**
7. **Explains limitations and failure modes**, not only advantages.
8. **Answers hidden questions** that users often discover only after purchase or use.
9. **Shortens the path to action**, rather than forcing the user to infer the conclusion.
10. **Contains a difficult-to-replace mechanism, dataset, comparison, or verification method.**

A strong page does not have to be long. Its strength comes from the number of uncertainties it resolves with minimal repetition.

## 5. Ten signs of a weak page

A weak page:

1. Starts with generic text that does not answer the user’s task.
2. Repeats category or industry clichés.
3. Replaces selection criteria with a list of benefits.
4. Uses “uniqueness” only at the level of wording.
5. Does not explain differences between similar options.
6. Ignores limitations, risks, and situations in which the advice does not apply.
7. Contains claims that cannot be verified.
8. Adds studies, figures, and facts without translating them into a practical mechanism.
9. Hides the main answer in the middle of the page.
10. Could be replaced by a typical competitor page without meaningful loss of value.

# Module A — Core Page Logic

## A1. Define the job to be done

Before writing, answer:


Who is the user?
What situation are they in?
What decision are they trying to make?
What do they not know?
What mistake are they trying to avoid?
What action should they take after using the page?


Use this format:


User:
Situation:
Decision:
Main uncertainty:
Main risk:
Desired next action:


If the page’s task is unclear, clarify or reconstruct it before writing.

## A2. Define the topic core

The topic core is the minimum semantic core without which the page stops answering its primary request.

It includes:

- the main object;
- the primary user question;
- mandatory entities;
- key selection criteria;
- necessary context;
- required evidence or limitations.

The topic core is not the full page. It defines the lower boundary of relevance.

## A3. Separate essential from optional content

Classify potential blocks as follows.

### Core

The page is substantively incomplete without them.

### Decision-support

They help users compare, choose, verify, or reject.

### Supporting

They improve confidence or understanding but are not essential.

### Decorative

They create an appearance of completeness but barely affect the decision.

Do not include decorative blocks merely to increase length.

## A4. Build the decision map

Use this structure:

| Decision stage | User question | Needed information | Page block |
|---|---|---|---|
| Scenario | Will this suit me? | Use cases | Scenario block |
| Filter | What should I rule out immediately? | Disqualifiers | Filter |
| Comparison | How do the options differ? | Comparable criteria | Comparison |
| Verification | How can I check suitability? | Measurement, test, or checklist | Verification instruction |
| Trust | Why should I believe this? | Data, reviews, or method | Evidence block |
| Action | What should I do next? | Next step | CTA or navigation |

# Module B — Decision Map and Missing Nodes

## B1. Search for missing nodes

A missing node is a potentially important information node that users need for a decision but competitors frequently omit.

Check five directions.

### 1. Failure mode

What can go wrong?

Examples:

- size mismatch;
- incorrect use;
- incompatibility;
- misinterpretation of a result;
- hidden additional cost;
- mismatch between expectation and reality.

### 2. Hidden information

What does the user usually discover too late?

Examples:

- actual measurements;
- care requirements;
- delivery limitations;
- the need for an additional accessory;
- actual fit;
- setup time;
- compatibility with other products.

### 3. Limitation

When does the recommendation stop working?

Examples:

- a different use case;
- a different load level;
- wearing under another layer;
- a different age or size;
- unusual conditions;
- missing infrastructure.

### 4. Disqualifier

Why should the user reject an option?

Examples:

- unsuitable cut or format;
- missing certification;
- insufficient compatibility;
- unacceptable delivery time;
- unsuitable return conditions;
- an operational feature the user cannot accept.

### 5. Quantifiable property

What can be measured?

Examples:

- height;
- shoulder width;
- volume;
- weight;
- speed;
- delivery time;
- number of steps;
- completion time;
- error rate;
- total cost of ownership.

Missing-node status is only an initial utility signal, not an automatic reason to include a block. Every candidate must still pass checks for:

- relevance;
- evidence;
- applicability;
- necessity;
- replaceability.

## B2. Convert a missing node into an intervention

A missing node should become a practical page element:


Missing node
    → user risk
    → decision question
    → mechanism
    → page intervention
    → required data
    → success metric


Possible interventions include:

- a filter;
- a comparison table;
- a calculator;
- a measurement guide;
- a scenario selector;
- a warning;
- a checklist;
- a verification instruction;
- a review summary;
- a limitation map;
- a before-and-after example;
- a “who this is not for” block.

# Module C — Research Layer

## C1. Research is not always necessary

First determine whether the problem can be solved using:

- first-party data;
- analytics;
- customer reviews;
- support requests;
- return data;
- expert review;
- internal search logs;
- previous test results;
- operational documentation.

Research escalation is justified when at least one of the following applies:

- there is a meaningful unknown about the cause of behavior;
- a disputed mechanism needs checking;
- the decision depends on human error or a cognitive limitation;
- an important claim requires external evidence;
- a non-obvious intervention is needed;
- internal evidence is incomplete or contradictory;
- the cost of being wrong is high.

Do not start a research pipeline:

- merely to add authoritative citations;
- if the research will not change the page;
- if sufficient verifiable first-party data already exists;
- when only a basic fact is needed;
- if the result cannot be converted into a mechanism or action.

## C2. Research angles

Search for answers to specific questions, not merely for “papers about the topic”:

- Why do users make this mistake?
- Where does uncertainty arise?
- What does the user discover too late?
- Which risk can be reduced?
- What affects the actual choice?
- Which mechanism explains the observed behavior?
- What can be measured?
- Which filter or page block should be added?
- When does the recommendation stop applying?
- Which options do users incorrectly treat as equivalent?

Every research angle must connect to the decision map or a missing node.

## C3. Four research roles

### Discovery

Research helps identify:

- a new risk;
- an unknown mechanism;
- an omitted scenario;
- a hidden selection criterion.

### Validation

Research checks:

- an existing hypothesis;
- an observation from reviews;
- a suspected cause of error;
- a link between an intervention and an outcome.

### Constraint

Research shows:

- when advice does not work;
- for which audiences it does not apply;
- which conditions limit transfer;
- which variables cannot be ignored.

### Measurement

Research helps select:

- a metric;
- an experiment design;
- a measurement method;
- a control group;
- an intermediate indicator.

## C4. Research Value Score

Rate candidate sources from 1 to 5 on:

- $R$ — relevance;
- $P$ — practicality;
- $E$ — evidence strength;
- $N$ — novelty;
- $T$ — transferability.

$$
\text{Research Value}
=
0.30R
+
0.25P
+
0.20E
+
0.15N
+
0.10T
$$

Working thresholds:


Research Value ≥ 3.5
Practicality ≥ 3


This is an operational GIST setting, not a universal scientific standard.

A study with high evidence strength but low transferability may be less useful than a study with somewhat weaker evidence that concerns the same user, scenario, and decision type.

## C5. Evidence levels

Use the following scale.

### Level A — Direct evidence

The evidence directly matches:

- the user;
- the scenario;
- the product or interface;
- the measurable outcome.

### Level B — Strong adjacent evidence

The context differs, but the mechanism and decision type are sufficiently close.

### Level C — Indirect evidence

The study supports a general mechanism, but transfer requires caution.

### Level D — Hypothesis-supported

There is a plausible hypothesis, preliminary evidence, or a limited experiment.

### Level E — Speculation

The claim is based on intuition, expert opinion, or an idea without adequate verification.

Evidence level does not replace transferability assessment.

## C6. Transfer risk

Assess transfer separately.

### Direct transfer

The result can be applied directly to the same audience and task.

### Partial transfer

The mechanism is probably relevant, but the context requires adaptation.

### Hypothesis only

The study is useful as a source of hypotheses, not as proof of the final intervention.

Do not:

- automatically transfer adult research to children’s pages;
- transfer offline behavior to a production interface without checking;
- treat purchase intention as actual purchase;
- treat a prototype as a proven CRO intervention;
- treat a laboratory result as a guaranteed commercial effect;
- transfer a result across cultures, audiences, or categories without qualification.

## C7. Research insight card

Record every used source in this format:


Paper:
Link:
Research question:
Context:
Method:
Evidence level:
Main finding:
Mechanism:
Practical implication:
Page block:
Required data:
Limitation:
Transfer risk:
Metric:
Test design:


The practical output should contain not a paper summary, but:

- the mechanism;
- the limitation;
- the page intervention;
- the required data;
- the metric or test hypothesis.

If research does not produce a mechanism, UX intervention, data requirement, or testable hypothesis, it should not appear in the practical recommendation.

## C8. Research diversity

Do not collect multiple sources that support the same point unless they provide different functions.

Aim to cover different decision angles, such as:

- size and fit;
- visual information;
- reviews and trust;
- search relevance;
- cognitive load;
- product relations;
- cold-start problems;
- operational friction;
- risk and failure;
- measurement.

## C9. Research conflicts

If studies conflict:

1. do not hide the conflict;
2. check differences in audience;
3. check differences in task;
4. check differences in metrics;
5. check differences in conditions;
6. state where each result applies;
7. do not make a stronger conclusion than the evidence permits.

# Module D — Content Selection and Compression

## D1. Score every block before writing

Use this table:

| Block | Utility | Diversity | Evidence | Actionability | Replaceability | Redundancy |
|---|---:|---:|---:|---:|---:|---:|
| Block A | 1–5 | 1–5 | 1–5 | 1–5 | 1–5 | 0–5 |

A high replaceability score means high replaceability and is therefore negative.

### Redundancy scale

| Risk | Meaning |
|---:|---|
| 0 | Clearly additive |
| 3 | Common but partly necessary |
| 5 | Fully generic or duplicated |

For convenience:

$$
D = 5 - \text{Redundancy Risk}
$$

This does not replace qualitative analysis.

## D2. Optional Content Value formula

For repeatable audits, team review, or automated scoring, use the following optional formula:

$$
\text{Content Value}
=
0.35U
+
0.25D
+
0.25X
+
0.15N
$$

where:

- $U$ — utility;
- $D$ — diversity value;
- $X$ — distinctiveness;
- $N$ — necessity.

Use a consistent 1–5 scale for each variable.

This formula is an **optional scoring aid**, not a mandatory mathematical representation of every editorial decision. It does not replace:

- topic-core validation;
- semantic-conflict analysis;
- evidence assessment;
- transfer-risk assessment;
- replaceability testing;
- editorial judgment about whether the block is necessary.

Do not create false precision by treating the score as more reliable than the evidence and assumptions behind it.

## D3. Core compression

First formulate the topic core in its minimal form.

Then check:

- Can words be removed without losing the decision?
- Does the new block repeat an existing block?
- Is the main criterion hidden?
- Is an example being used instead of a rule?
- Is a generic recommendation replacing a concrete filter?

Compression must not remove:

- a limitation;
- an exclusion;
- a material risk;
- evidence;
- a selection criterion;
- a verification method.

## D4. Early differentiation

The main difficult-to-replace meaning should appear early:

- above the fold;
- in the first substantive block;
- near the beginning of the title or description;
- before a long generic explanation.

Do not postpone the key filter, limitation, or criterion until the end of the page.

## D5. Evidence over reassurance

Prefer:


Observable fact
    → explanation of mechanism
    → practical consequence
    → verification method


Over:


General promise
    → emotional intensification
    → templated CTA


## D6. Edge-case heuristic

An edge case is useful when it is:

- sufficiently likely;
- connected to a serious mistake;
- decision-changing;
- capable of filtering out an unsuitable option in advance.

Do not add rare cases merely to create an appearance of completeness.

## D7. Scenario heuristic

Test every important claim through a scenario:


For whom?
When?
Under what conditions?
What changes?
How can it be checked?


Advice without a scenario is often too general to be applied.

## D8. Conflict heuristic

Look for tensions such as:

- low price versus total cost of ownership;
- visual appeal versus practicality;
- speed versus accuracy;
- universality versus task fit;
- simplicity versus control;
- broad choice versus decision complexity.

A conflict often creates a more useful block than another benefit.

## D9. Friction heuristic

Identify what prevents action:

- an unclear next step;
- too many options;
- missing measurements;
- unclear return conditions;
- difficult verification;
- no comparison;
- distrust of reviews;
- a long path to the result.

A strong page does not only inform; it reduces friction.

## D10. Fallback before filler

If unique and well-supported facts are limited:

1. use a verifiable operational fact;
2. add scenario-specific detail;
3. add a limitation;
4. add a verification method;
5. compress generic material;
6. only then use a neutral fallback.

Fallback does not waive the other filters. Relaxing one requirement does not remove the need for:

- relevance;
- verifiability;
- usefulness;
- non-duplication;
- clarity;
- accuracy;
- low replaceability.

# Module E — Structural Fields

Titles, meta descriptions, and headings are not merely technical summaries. They are independent entry points into the page’s meaning.

They may be used in:

- search results;
- social previews;
- AI summaries;
- internal catalogs;
- voice responses;
- navigation;
- link cards.

## E1. Four filters for meta fields

Every candidate meta claim must pass four filters:

1. **Specificity** — Is it concrete?
2. **Significance** — Does it affect perception or decision-making?
3. **Replaceability** — Is it difficult to replace with a generic phrase?
4. **Verifiability** — Can the claim be checked?

## E1a. Meta fallback sequence

If no candidate passes all four filters, use the following sequence.

### 1. Super-category fact

Check the brand, product line, service line, or broader category for a verified inherited fact.

The fact must remain relevant to the specific page and must not be presented as a page-specific property if it is only true at the parent level.

### 2. Relax verifiability only

Allow a concrete, decision-relevant, non-replaceable fact that is not yet verifiable on the page.

If this path is used:

- label the fact internally as requiring verification;
- add verifiable proof to the description or page;
- create an owner and update trigger where appropriate;
- do not convert the claim into a guarantee.

### 3. Structural or operational fact

Use a concrete fact about:

- service;
- delivery;
- support;
- compatibility;
- availability;
- configuration;
- ordering;
- returns;
- implementation.

The fact must still pass relevance, accuracy, replaceability, and practical significance checks.

### 4. Human escalation

If all previous paths fail, output:


No GIST-compliant differentiating fact was found. Manual review required.


Do not fill the field with:

- abstract quality language;
- generic category facts;
- unsupported superlatives;
- a weak stack of benefits;
- a random number;
- a templated CTA.

### 5. Non-negotiable fallback rule

Fallback does not permit abstract quality language and does not waive:

- relevance;
- replaceability;
- accuracy;
- clarity;
- user usefulness;
- temporal validity where applicable.

## E2. Title

A title should:

- identify the object quickly;
- match search intent;
- contain one strong differentiator;
- avoid stacking multiple weak benefits;
- avoid promising something absent from the page;
- use a stable fact unless the page concerns a controlled campaign.

Practical Cyrillic-oriented guidelines:

- approximately 40–50 characters;
- place the main GIST fact within the first 35 characters when possible;
- use approximately 600 px as a width reference.

These are not hard limits. Actual display depends on font, device, and interface.

## E3. Meta description

A description should:

- expand or apply the title’s claim;
- add new proof, a scenario, a filter, or an action;
- avoid repeating the title verbatim;
- remain understandable without additional context;
- avoid unsupported superlatives;
- account for mobile display.

Practical Cyrillic-oriented guidelines:

- desktop: approximately 130–145 characters;
- mobile: approximately 90–105 characters;
- place the main fact within the first 90 characters when possible;
- use approximately 920 px as a desktop width reference;
- use approximately 680 px as a mobile width reference.

Search engines may rewrite the description. The goal is therefore to provide the best source of meaning, not to force the system to display the exact text.

## E4. Standalone exposure

By default, title and description should perform different functions.

Some repetition is justified when the description may appear separately from the title:

- in social previews;
- in AI answers;
- in voice search;
- in link previews;
- in messaging applications;
- in internal content cards.

In that case:

1. put the repeated fact at the beginning of the description;
2. follow it with new proof, a scenario, or an application detail;
3. do not turn the description into a literal copy of the title.

If a page is actively shared on social networks, define a separate `og:description`. Do not rely on the meta description as the only source for social-preview text.

## E5. Temporal stability

Separate:

### Stable facts

- material;
- intended use;
- permanent compatibility;
- method of use;
- stable characteristics;
- durable selection criteria.

### Time-bound facts

- promotions;
- inventory;
- delivery time;
- season;
- current price;
- temporary availability;
- review count;
- certification or verification status.

Stable facts are generally preferable in titles.

Every temporary GIST factor must have:


Temporary GIST factor:
Owner:
Review date:
Update trigger:
Fallback text:


Do not use a temporary fact without an owner and review date.

## E6. Meta anti-patterns

Avoid:

1. abstract qualities without evidence;
2. generic category facts;
3. stacking several weak benefits;
4. repeating the brand without a semantic function;
5. random numbers;
6. templated CTAs;
7. verbatim repetition of the title;
8. temporary facts without a review date;
9. operational facts without checking their current validity;
10. promises about functions that do not exist on the page;
11. uniqueness created only through unusual wording;
12. unsupported superlatives;
13. placing the fact too late;
14. wording that violates the user’s likely expectation;
15. fallback text that has not passed replaceability and verifiability checks.

# Module F — Page-Type Adaptation

The GIST factor must fit the page type.

| Page type | Strong GIST factors |
|---|---|
| Product | Compatibility, measurable property, use case, limitation |
| Category | Selection filter, size logic, subtype comparison, scenarios |
| Local service | Geography, timing, booking method, verifiable operational fact |
| SaaS/B2B | Integration, implementation process, user role, limitation |
| Blog or guide | Non-obvious mechanism, verification method, user error |
| Comparison | Shared criteria, suitability by user, trade-off |
| Landing page | Outcome, mechanism, proof, qualification |
| FAQ | Real question, concrete answer, exception, next step |
| News or research | Novelty, date, source, practical meaning, limitation |

## F1. Informational guide

Include:

- the main question;
- the cause or mechanism;
- possible solutions;
- a limitation;
- a way to verify the result;
- a next step.

## F2. Comparison page

Do not compare only specifications. Compare:

- scenarios;
- selection criteria;
- limitations;
- total cost of ownership;
- compatibility;
- complexity;
- expected result.

For each option, answer:


Who is it for?
Who is it not for?
What trade-off does the user accept?
How can the choice be verified?


## F3. Category page

A category page should help users:

- choose a direction quickly;
- apply a filter;
- understand differences;
- check size or compatibility;
- reach the appropriate product or subcategory.

Do not turn category copy into a universal article about the entire subject area.

## F4. Review page

A review should distinguish:

- expectation;
- actual use case;
- measurable experience;
- limitation;
- user context.

Do not treat one review as universal evidence.

## F5. FAQ

An FAQ should address real barriers:

- before purchase;
- before use;
- before return;
- before registration;
- before comparison;
- after a problem occurs.

Do not add questions merely to increase semantic volume.

# Module G — Evidence, Transfer, and Claims

## G1. Claim levels

Assign every important claim an evidence level:


A — directly supported by relevant data;
B — supported by strong adjacent evidence;
C — indirectly supported;
D — working hypothesis;
E — assumption or speculation.


The higher the decision risk, the stronger the evidence should be.

## G2. Claim structure

Prefer:


Claim
    → evidence
    → context
    → limitation
    → practical implication


Do not convert a probabilistic statement into a guarantee.

## G3. Research and final copy

The final user-facing text should contain:

- the conclusion;
- the mechanism;
- the practical consequence;
- the limitation;
- the application or verification method.

Do not include a long methodological summary unless it changes the user’s decision.

## G4. First-party and external data

First-party data may be more useful than external research when it:

- concerns the same audience;
- concerns the same product;
- comes from the real use scenario;
- has a clear method;
- is updated regularly;
- does not mistake correlation for causation.

# Module H — Metrics and Experiments

## H1. Metrics must follow the intervention

Do not choose a metric merely because it is easy to obtain.

The relationship should be:


Page intervention
    → expected behavior
    → primary metric
    → guardrail metric
    → test design


## H2. Example metrics

### Selection filter

- transition to the appropriate subcategory;
- reduction in returns;
- reduction in unsuitable selections;
- filter usage;
- subsequent selection accuracy.

### Size or measurement block

- use of the sizing tool;
- reduction in size-related returns;
- reduction in fit-related support requests;
- completion of the measurement check.

### Comparison block

- transition to a selected option;
- shorter decision time;
- fewer backtracks;
- increased clicks on a qualified CTA.

### Trust block

- engagement with reviews;
- transitions to evidence;
- lower abandonment during the decision stage;
- improved quality of support questions.

### Research-based intervention

- a metric directly tied to the proposed mechanism;
- a control measure;
- an interpretation limit;
- a predefined success criterion.

Do not use clicks as a substitute for the target outcome when clicks are not the final action.

## H3. Test design

For every testable idea, specify:


Hypothesis:
Audience:
Control:
Variant:
Primary metric:
Guardrail metric:
Expected direction:
Minimum useful effect:
Test duration:
Known confounders:
Decision rule:


# Module I — Audit Modes

## I1. Content audit

Check:

- Is the job to be done clear?
- Is the topic core present?
- Does every block help the user decide?
- Is there semantic duplication?
- Were missing nodes checked?
- Are limitations present?
- Can key claims be verified?
- Is a generic promise replacing a mechanism?

## I2. Research audit

Check:

- Was research genuinely necessary?
- Is every source connected to a decision node?
- Was a mechanism extracted?
- Is the evidence level stated?
- Is transfer risk stated?
- Is transferability being overestimated?
- Does the source add a new function?
- Is there a page intervention?
- Is there a metric or testable hypothesis?

## I3. Meta audit

Check:

- Is there a concrete differentiator?
- Does it appear early?
- Do title and description perform different functions?
- Was the fallback sequence followed?
- Is a temporary fact used without an owner?
- Was pixel width checked?
- Is a separate `og:description` needed?
- Can the claim be verified?
- Does the text sound like a generic template?

## I4. Replaceability audit

For every important block, ask:


Could this block be copied in five minutes?
If yes, what should be added:
- first-party data;
- a scenario;
- a filter;
- a limitation;
- a verification method;
- a mechanism;
- a comparison;
- evidence?


## I5. Compression audit

Remove or combine a block if:

- it repeats an existing point;
- it does not change the decision;
- it adds only wording-level novelty;
- it lacks evidence;
- it lacks a scenario;
- it lacks an action;
- it does not address a meaningful risk.

# Module J — Creation Mode and Output

## J1. Creation mode

When creating a page:

1. Define the user job.
2. Define the topic core.
3. Build the decision map.
4. Search for missing nodes.
5. Select the smallest reliable module set.
6. Decide whether research escalation is necessary.
7. If necessary, formulate research angles.
8. Score candidate sources using Research Value.
9. Convert selected sources into insight cards.
10. Generate candidate page blocks.
11. Score utility, diversity, evidence, actionability, replaceability, and redundancy.
12. Optionally calculate Content Value.
13. Compress the core.
14. Place the main differentiator early.
15. Adapt the structure to the page type.
16. Create the title, description, and headings.
17. Apply the meta fallback sequence if needed.
18. Assign metrics and tests.
19. Run content, research, meta, and replaceability audits.
20. Check temporal stability.
21. Remove anything that fails the filters.
22. Produce the final page or implementation brief.

## J2. Audit mode

When asked to audit a page, do not immediately rewrite it.

First provide:


1. What already works.
2. What is repetitive.
3. Which decision nodes are missing.
4. Which claims require evidence.
5. Which limitations are undisclosed.
6. Which blocks are replaceable.
7. What should be removed.
8. What should be added.
9. Which metrics should be checked.
10. The priority of each change.


Use the smallest audit scope that can answer the request reliably.

## J3. Research mode

When asked for a research-based analysis:

1. Formulate research angles.
2. Separate discovery from validation.
3. Show the selection criteria.
4. State the evidence level.
5. State transfer risk.
6. Separate fact, interpretation, and hypothesis.
7. State the mechanism and page intervention for every selected source.
8. Identify required data and metrics.
9. Exclude sources that do not change the practical decision.
10. Escalate to deeper research only when unresolved uncertainty remains.

## J4. Meta mode

When the task concerns title and description:

1. Determine whether the relevant fact is stable or temporary.
2. Select one primary GIST factor.
3. Apply the four meta filters.
4. Run the fallback sequence if no candidate passes.
5. Write the title.
6. Write a description with a different function.
7. Check standalone exposure.
8. Check whether a separate `og:description` is needed.
9. Check Cyrillic-aware display width where relevant.
10. Check whether the wording is a generic competitor template.
11. Record the owner and update trigger for temporary facts.

## J5. Output discipline

When presenting recommendations, distinguish clearly between:


Verified fact:
Interpretation:
Hypothesis:
Recommended page intervention:
Required evidence:
Metric:
Open uncertainty:


Do not present an interpretation or hypothesis as a verified fact.

# Module K — Final Checklists and Non-Negotiable Principles

Before publication, answer each question with “yes” or “no.”

## K1. Page logic

- Is it clear what task the page solves?
- Is it clear who the page is for?
- Is it clear what decision the user should make?
- Are selection criteria present?
- Are filters and exclusions present?
- Is there a clear next step?

## K2. Utility and diversity

- Does every block add useful meaning?
- Does any block repeat another?
- Are there different types of decision support?
- Has wording-level novelty been confused with substantive novelty?
- Has irrelevant novelty been added?
- Was the smallest sufficient content set selected?

## K3. Missing nodes

- Were failure modes checked?
- Was hidden information checked?
- Are limitations stated?
- Are disqualifiers present?
- Are measurable properties or verification methods present?

## K4. Research

- Was research genuinely necessary?
- Is every source connected to a specific decision node?
- Was a mechanism extracted?
- Are evidence level and transfer risk stated?
- Did the source become a page intervention, data requirement, or test hypothesis?
- Is research being used as decoration?
- Was research depth proportionate to the task?

## K5. Evidence

- Are key claims verifiable?
- Has a hypothesis been presented as a fact?
- Has a result been transferred beyond its context?
- Has purchase intention been presented as actual purchase?
- Are limitations stated?
- Are first-party and external evidence clearly distinguished?

## K6. Meta

- Is there one strong, specific GIST fact?
- Do title and description perform different functions?
- Does the description work when shown alone?
- Was the fallback sequence followed when necessary?
- Is a separate `og:description` needed?
- Were temporal stability and review dates checked?
- Were title and description widths checked?
- Does the text avoid generic templates?
- Are temporary claims assigned an owner and update trigger?

## K7. Actionability

- Is it clear what the user should do?
- Can the result be checked?
- Is there an appropriate metric?
- Has the target metric been replaced by clicks?
- Is there a guardrail metric?
- Is the proposed intervention operationally possible?

## K8. Compression

- Were generic introductions removed?
- Were repetitive blocks compressed?
- Is the main answer visible early?
- Was text added only for completeness?
- Were limitations, evidence, and selection criteria preserved during compression?

## K9. Modular routing

- Were only the necessary modules activated?
- Were required modules not skipped?
- Was the depth of analysis proportional to uncertainty and decision risk?
- Was escalation triggered where factual, research, competitive, transfer, or measurement uncertainty remained?

# What the LLM must never forget

1. A strong page does not have to be complete or long.
2. New wording is not a new advantage.
3. A missing node is a candidate for utility, not an automatic page element.
4. Utility without diversity creates repetition.
5. Diversity without utility creates irrelevant novelty.
6. The main differentiator should be clear early.
7. A generic recommendation is weaker than a concrete filter, scenario, or verification method.
8. Research without a mechanism does not belong in the practical answer.
9. Evidence strength and transferability are separate parameters.
10. High scientific credibility does not justify an invalid contextual transfer.
11. A temporary fact requires an owner, review date, update trigger, and fallback.
12. Title and description are a two-field system with distinct functions.
13. A description may be displayed independently of its title.
14. If social distribution matters, define a separate `og:description`.
15. The meta fallback sequence must be followed before using filler.
16. Fallback never permits abstract quality language.
17. Fallback does not waive relevance, replaceability, accuracy, or clarity.
18. Relaxing one fallback filter does not waive the others.
19. The page should reduce uncertainty, not merely increase information volume.
20. Every block must have an architectural role.
21. Every substantial recommendation should connect to a scenario, limitation, or verification method.
22. Research citations do not replace editorial judgment.
23. First-party evidence may be more useful than external research when it matches the actual audience and scenario.
24. Content scoring supports judgment but does not replace it.
25. A numerical score must not create false precision.
26. The smallest reliable module set should be used for each task.
27. Modularity reduces unnecessary work; it does not reduce mandatory checks.
28. The final objective is difficult-to-replace usefulness, not textual uniqueness.

## Final definition

> GIST is a modular process for selecting and designing semantic blocks that are simultaneously useful, diverse, evidence-aware, applicable, actionable, and difficult to replace, while reducing decision risk and shortening the user’s path to the right action.
