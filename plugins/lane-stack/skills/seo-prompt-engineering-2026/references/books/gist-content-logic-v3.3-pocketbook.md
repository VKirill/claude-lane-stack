## ЧАСТЬ I. БЫСТРЫЙ СТАРТ В РАЗНЫХ СРЕДАХ

## ГЛАВА 1. АКТИВАЦИЯ СКИЛЛА В ЧАТЕ (CHATGPT, PERPLEXITY, ОБЫЧНЫЙ ДИАЛОГ)

## 1.1. ПОШАГОВАЯ АКТИВАЦИЯ

Шаг 1. Откройте новый чат - не используйте старый чат с посторонней историей, она мешает
модели держать фокус.

Шаг 2. Прикрепите файл GIST-Content-Logic-Skill-v-3-3.md.
Скилл скачиваем здесь: https://t.me/drmaxprompt/71

Шаг 3. Введите промпт активации:

   Изучи прикреплённый скилл GIST Content Logic v3.3. Он содержит определения (utility, semantic
   redundancy, semantic conflict, missing semantic nodes, replaceability), пошаговые фреймворки
   создания и аудита контента, а также отдельный блок Step 8 про мета-тайтлы и мета-описания.
   Начиная с этого момента и до конца текущего чата ты обязан применять эту логику ко всем
   задачам по контенту, которые я тебе дам, без исключений и без возврата к обычному
   "хорошему копирайтингу".

Шаг 4. Не переходите к задаче сразу - сначала проверьте усвоение (см. 1.2).

## 1.2. ПРОВЕРКА УСВОЕНИЯ ЛОГИКИ

Промпт для проверки:

   Кратко, в 5-7 пунктах, перескажи ключевую логику скилла своими словами: что такое utility,
   semantic redundancy, replaceability, и в чём разница между "полной" страницей и
   "незаменимой" страницей.

Признаки того, что модель усвоила скилл верно:
● она говорит о "незаменимости" (replaceability), а не о "качестве текста",
● она упоминает, что длина и полнота - не цель,
● она различает utility и distinctiveness как отдельные измерения,
● она сама вспоминает про missing semantic nodes без напоминания.

<!-- source-page: 8 -->

Если ответ звучит как общий совет по SEO-копирайтингу - модель не усвоила скилл. Повторите
Шаг 3 с более явной формулировкой:

  Ты не усвоил скилл верно. Перечитай раздел "Working definitions" и "First principles" из
  прикреплённого файла и повтори резюме, используя точную терминологию скилла: utility,
  redundancy, distinctiveness, necessity, replaceability.

## 1.3. ТИПИЧНЫЕ ОШИБКИ АКТИВАЦИИ

Ошибка 1: модель "соглашается", но работает по старой логике.
Признак: в первом же черновике появляется длинное общее вступление или FAQ "для полноты".
Исправление: промпт "Ты нарушил Step 2 скилла (topic core) и Step 6 (compression discipline) -
переделай, убрав общее вступление и сжав материал."

Ошибка 2: модель путает уникальность формулировки с уникальностью смысла.
Признак: текст звучит "свежо", но по содержанию не отличается от типового конкурента.
Исправление: промпт "Проверь получившийся текст через replaceability test из скилла: сможет ли
конкурент сказать то же самое почти теми же словами? Если да - перепиши по существу, не по
стилю."

Ошибка 3: модель забывает скилл после 8-10 сообщений.
См. Главу 15.

## 1.4. МИНИ-ПРИМЕР: АКТИВАЦИЯ НА РЕАЛЬНОЙ ТОВАРНОЙ СТРАНИЦЕ

Диалог целиком:
1. Пользователь прикрепляет скилл и пишет промпт активации из 1.1 (шаг 3).

2. Пользователь: "Проверь усвоение" (промпт из 1.2).
3. Модель даёт корректное резюме.
4. Пользователь: "Теперь применяем скилл к товарной странице: ламинат Praktik. Вот текст
текущей страницы: [вставка]. Проведи Audit mode целиком."
5. Модель проводит Phase 1-8 аудита, включая проверку текущего title/description.
6. Пользователь: "Собери финальный вариант страницы и отдельно - title и description по Step 8."

Это базовый паттерн, который повторяется во всех остальных главах: активация → проверка →
задача → финальная сборка.

  информационной ценностью. Не создавай наполнитель. Перед сохранением каждой секции
  оценивай её пользу, избыточность, уникальность и необходимость.

## ГЛАВА 3. АКТИВАЦИЯ СКИЛЛА В АГЕНТНЫХ СИСТЕМАХ И АВТОПАЙПЛАЙНАХ

## 3.1. ВСТРАИВАНИЕ СКИЛЛА В СИСТЕМНЫЙ ПРОМПТ АГЕНТА

Для n8n, Make, кастомных ботов на API скилл целиком может не влезать в системный промпт с
учётом лимитов и стоимости вызова:

Шаг 1. Определите, какая часть скилла нужна конкретному агенту в пайплайне (см. 3.4).

Шаг 2. Для агента, создающего черновики - грузите Steps 1-7 и working definitions.

Шаг 3. Для агента, собирающего мета-поля - грузите отдельно Step 8 целиком.

Шаг 4. Для агента-аудитора - грузите Audit mode instructions и Section-level evaluation framework.

## 3.2. ПЕРЕДАЧА СКИЛЛА ЧЕРЕЗ API-КОНТЕКСТ БЕЗ ПОТЕРИ СТРУКТУРЫ

● сохраняйте markdown-разметку скилла как есть - заголовки Step/Phase помогают модели
 навигировать,
● не сокращайте working definitions - это ядро логики,
● если контекстное окно агента маленькое (менее 8000 токенов) - используйте сжатую версию

## 3.3. СОКРАЩЁННАЯ ВЕРСИЯ СКИЛЛА ДЛЯ АГЕНТОВ С МАЛЫМ ОКНОМ

Минимальный рабочий набор (примерно 1500-2000 токенов):

   Работай по методу GIST: контент - это задача выбора, не задача объёма. Правила: 1) Сохраняй
   смысловое ядро темы, но не раздувай его. 2) Убирай смысловую избыточность - блоки,
   которые говорят то же самое другими словами или то же самое, что говорят все конкуренты. 3)
   Ищи отсутствующие смысловые узлы: исключения, ограничения, кейсы отказа, критерии
   выбора, о чём молчат конкуренты. 4) Выноси самое ценное и неповторимое выше в структуре
   страницы. 5) Перед сдачей проверяй: сможет ли конкурент заменить эту страницу или блок
   почти без потерь? Если да - переделай. Никогда не путай длину текста с его пользой, а
   уникальность формулировки - с уникальностью смысла.

Для мета-полей отдельно:

<!-- source-page: 12 -->

  Для тайтла и описания страницы: выбери один конкретный, проверяемый факт (не общее
  слово вроде "качественный" или "лучший"), который решает реальное сомнение пользователя
  и который конкурент не может честно написать про себя. Если такого факта нет - ищи его
  через вопросы: что может пойти не так, что пользователь узнаёт слишком поздно, когда это не
  работает, кому это не подходит, что измеримо. Если и тогда факта нет - используй факт о
  категории целиком, либо факт об услуге (доставка, гарантия), но не выдумывай и не пиши
  общими словами. Тайтл и описание не должны повторять один и тот же факт разными
  словами.

## 3.4. ПРИЁМ "РАЗДЕЛЕНИЯ РОЛЕЙ" - МНОГОАГЕНТНАЯ СХЕМА

Агент 1 - "Разведчик конкурентов". Получает URL/тексты конкурентов, на входе - только Step 3
скилла. Отдаёт список shared core / shared redundancy / shared omissions.

Агент 2 - "Архитектор страницы". Получает вывод Агента 1 плюс Steps 1-2, 4-7. Собирает
структуру и черновик.

Агент 3 - "Мета-инженер". Получает финальный черновик от Агента 2 (для Cross-level
dependency note) плюс Step 8 целиком. Собирает и проверяет title/description.

Агент 4 - "Контролёр". Получает результат от Агентов 2-3 плюс Minimal operating checklist и Pre-
publish checklist. Проверяет и либо пропускает, либо отправляет на доработку конкретному
агенту.

## 3.5. МИНИ-ПРИМЕР: СВЯЗКА АГЕНТОВ ДЛЯ КАТАЛОГА ИЗ 50 ТОВАРОВ

1. На входе - список 50 товаров с характеристиками и 3-5 URL конкурентов на нишу.
2. Агент 1 один раз анализирует конкурентов по нише и отдаёт карту редундантности -
например, для линолеума: "все пишут про широкий выбор цветов, никто не пишет про подрезку
рулона под размер."
3. Агент 2 для каждого товара строит описание, используя найденный узел как основу угла.
4. Агент 3 собирает title/description по формуле Step 8.11: переменный слот - конкретная услуга
или характеристика, фиксированная часть - название товара и магазин.
5. Агент 4 проверяет весь список на диагностический порог 70% - если факт повторяется без
основания, сигнализирует о необходимости второго слота.

Итоговый пример пары: тайтл "Ламинат Praktik + восковая защита торцов Aqua Stop", описание
"Восковая защита Aqua Stop - ламинат не боится воды в швах. Класс 32, 8 мм. Замок Click - сборка
без клея. 1200+ отзывов. Доставка сегодня."

## ГЛАВА 4. СЦЕНАРИЙ "СТРАНИЦА С НУЛЯ" - ПОЛНЫЙ ПРОХОД

## 4.1. ПРОМПТ ДЛЯ ЗАПУСКА CREATION MODE ЦЕЛИКОМ

  Запусти Creation mode из скилла целиком, все 8 фаз последовательно: определи задачу
  страницы, вытащи ядро темы, проанализируй избыточность конкурентов (я прикреплю их
  страницы), выбери угол подачи, спроектируй структуру, напиши черновик с компрессионной
  дисциплиной, проведи самоаудит на заменяемость, и в конце отдельно собери title и
  description по Step 8. Не пропускай фазы и не объединяй их в одну.

Вводные: тема/запрос, тип страницы, ссылки или файлы конкурентов.

## 4.2. ПРОМПТ ДЛЯ ЗАПУСКА ТОЛЬКО PHASE 1-2

  Пройди только Phase 1 и Phase 2 из Creation mode. Не пиши структуру и не пиши текст.
  Определи: первичный и вторичные интенты запроса, тип страницы, какое решение должен
  принять пользователь, какую ошибку страница должна предотвратить. Затем отдельно
  выведи ядро темы - что обязательно должно быть на странице, и что явно не входит в ядро.

Запрос: "[ваш запрос]". Тип бизнеса/ниша: "[ниша]".

## 4.3. ПРОМПТ ДЛЯ ЗАПУСКА ТОЛЬКО PHASE 3

  Пройди только Phase 3 из Creation mode. Проанализируй прикреплённые страницы
  конкурентов и выведи четыре списка: необходимое ядро; избыточность без ценности;
  шаблонные паттерны; что все конкуренты упускают. Не предлагай пока структуру моей
  страницы.

Прикрепите 3-5 файлов конкурентов в текстовом виде.

## 4.4. ПРОМПТ ДЛЯ ВЫБОРА УГЛА ПОДАЧИ

  На основе найденной конкурентной избыточности и пропусков предложи три разных угла
  подачи для моей страницы. Для каждого укажи: в чём он делает страницу менее заменимой,
  какой у него риск, и какой отсутствующий узел он использует. Не выбирай угол сам - дай мне
  три варианта.

Приём при слишком похожих углах:

<!-- source-page: 14 -->

  Углы 1 и 2 слишком похожи по сути. Предложи третий вариант, который использует другой
  отсутствующий смысловой узел, а не вариацию того же самого.

## 4.5. ПРОМПТ ДЛЯ СБОРКИ СТРУКТУРЫ С FRONT-LOADING

  Спроектируй структуру страницы на основе выбранного угла [указать]. Обязательно вынеси
  самый ценный материал в первые два-три блока. Покажи структуру как список заголовков с
  одной строкой описания под каждым: роль блока и почему он не заменим типовым
  конкурентным блоком.

## 4.6. ПРОМПТ ДЛЯ ЧЕРНОВИКА С КОМПРЕССИОННОЙ ДИСЦИПЛИНОЙ

  Напиши черновик по утверждённой структуре. Правила: каждая идея выражена один раз,
  никаких повторных предупреждений в разных блоках, никаких абзацев, пересказывающих
  заголовок, никаких списков там, где хватит одного предложения, никакого FAQ для "остатков".

Приём контроля длины:

  Пройдись по черновику и для каждого абзаца ответь одним словом: сохраняет ли удаление
  этого абзаца ценность страницы? Если да - удали абзац и покажи финальную версию.

## 4.7. ФИНАЛЬНЫЙ САМОАУДИТ - ПРОМПТ-ЧЕК-ЛИСТ

  Проведи финальный самоаудит черновика. Ответь по каждому пункту да/нет с коротким
  объяснением: что можно убрать без потерь; что до сих пор звучит как типовой контент
  конкурентов; какая секция слишком легко заменяема; какой ценный факт стоит поднять
  выше; какой отсутствующий узел так и не был добавлен. Если хотя бы один ответ показывает
  высокую заменяемость - перепиши и покажи финальную версию.

## 4.8. СКВОЗНОЙ ПРИМЕР: КАТЕГОРИЯ ТОВАРОВ

Ниша: категория "кроссовки для бега". Запрос "купить кроссовки для бега" → задача страницы:
помочь выбрать модель из сотен вариантов; ядро - бренды, размеры, типы (амортизация,
стабильность, трейл/асфальт).

Конкурентный анализ (4 страницы) показывает: все перечисляют бренды и цены (ядро),
повторяют "широкий выбор" и "быстрая доставка" (избыточность), никто не даёт подбор по
пронации и типу поверхности (упущение).

Выбранный угол: готовая матрица подбора "тип поверхности + тип стопы + уровень подготовки
→ 3 модели" - прямое решение найденного упущения.

Структура: матрица подбора идёт сразу после короткого вступления, а не в конце; общий текст
"почему бег полезен" убирается целиком. Блок "когда менять кроссовки" добавляется как
отсутствующий у конкурентов узел.

Итоговая структура: заголовок → матрица подбора (3 строки) → сетка товаров с фильтром по
типу стопы → "когда менять кроссовки" → минимальный FAQ (2 вопроса).

## ГЛАВА 5. СЦЕНАРИЙ "ПЕРЕПИСАТЬ СУЩЕСТВУЮЩУЮ СТРАНИЦУ" - AUDIT MODE

## 5.1. ПРОМПТ ДЛЯ РЕКОНСТРУКЦИИ ЗАДАЧИ СТРАНИЦЫ

## 5.2. ПРОМПТ ДЛЯ РАЗБИВКИ НА БЛОКИ С ОЦЕНКОЙ

  Разбей страницу на смысловые блоки (не по HTML-тегам). Для каждого укажи: назначение,
  оценку пользы, избыточности, уникальности и риск заменяемости конкурентом.

## 5.3. ПРИЁМ "ТАБЛИЦА ПРИГОВОРОВ"

  Сведи результат в таблицу: блок, оценки (польза/избыточность/уникальность), решение
  (оставить/сжать/переписать/объединить/переместить выше/переместить ниже/удалить),
  краткое обоснование в одной строке.

## 5.4. ПРОМПТ ДЛЯ ПОИСКА ОТСУТСТВУЮЩИХ СМЫСЛОВЫХ УЗЛОВ

  Отдельно ответь: какие критические вопросы пользователя остаются без ответа; какие
  решения читателя недостаточно поддержаны аргументами; какие кейсы отказа или
  ограничения не упомянуты; какие сценарии не разделены, хотя должны быть.

## 5.5. ПРОМПТ ДЛЯ ПЕРЕУПОРЯДОЧИВАНИЯ СТРУКТУРЫ БЕЗ ПЕРЕПИСЫВАНИЯ

  Не переписывая текст блоков, предложи новый порядок структуры: какие блоки поднять
  выше, какие опустить, какие объединить. Обоснуй каждое перемещение.

## 5.6. ПРОМПТ ДЛЯ ФИНАЛЬНОЙ ПЕРЕПРОВЕРКИ "БЫЛО/СТАЛО"

  Сравни исходную и переписанную версию по тесту на заменяемость. Опиши разницу
  конкретно: что именно в новой версии делает страницу менее заменимой.

## 5.7. СКВОЗНОЙ ПРИМЕР: АУДИТ СТРАНИЦЫ УСЛУГИ

Ниша: "ремонт стиральных машин на дому". Задача страницы - снять тревогу перед вызовом
мастера и убедить оставить заявку здесь, а не у конкурента.

Таблица приговоров: вступление про важность техники - удалить. Список неисправностей (есть у
всех) - сжать. "Почему выбирают нас" (общие фразы) - переписать с конкретными фактами. FAQ (6
из 8 вопросов дублируют текст) - сжать до 2 реальных вопросов.

Отсутствующие узлы: нет ответа "сколько стоит вызов, если мастер не смог починить", нет
гарантии на запчасти, нет времени приезда по районам.

отказе → сжатый список неисправностей → 2 реальных FAQ → форма заявки. Старая версия легко
заменяема, новая содержит конкретные операционные факты, которых нет у всех конкурентов.

## ГЛАВА 6. СЦЕНАРИЙ "ТОЛЬКО КОНКУРЕНТНЫЙ АНАЛИЗ" БЕЗ ПЕРЕПИСЫВАНИЯ

## 6.2. ПРИЁМ "МАТРИЦА ПРОБЕЛОВ"

## 6.3. КАК ПЕРЕДАТЬ РЕЗУЛЬТАТ КАК ТЕХЗАДАНИЕ КОПИРАЙТЕРУ

 2) обязательное ядро; 3) чего избегать; 4) что обязательно добавить с пояснением; 5)

## 7.4. ПОЛНАЯ ОЦЕНКА ВСЕХ БЛОКОВ ЗА ОДИН ПРОХОД

скилла за один проход, без разделения на два запроса:

  Разбей прикреплённый текст на смысловые блоки (не по HTML-тегам, а по смыслу). Для
  каждого блока заполни таблицу:
  Правила принятия решения:
   ● Essential + Low redundancy → оставить
   ● Essential + Medium/High redundancy → сжать
   ● Helpful + Low distinctiveness → переписать или объединить
   ● Optional + High/Critical redundancy → удалить
   ● High Distinctiveness + High Utility → переместить выше
  После таблицы отдельно перечисли блоки для перемещения выше и блоки для удаления.

Этот промпт заменяет двухшаговую процедуру из 5.2 + 5.3 одним проходом и даёт готовую
таблицу для передачи редактору.

## 7.5. ТОЧЕЧНЫЙ ЗАПУСК ЭВРИСТИК

Когда нужно проверить только один аспект страницы без полного цикла аудита - используйте
один из этих коротких промптов.

Conflict heuristic: Найди в тексте блоки, которые делают одну и ту же информационную работу с
перекрывающимся смыслом - например, введение и FAQ повторяют одни и те же
предупреждения. Укажи, какие блоки нужно объединить, а какие - удалить.

Early-differentiation heuristic: Прочитай первые 30% текста. Определи: самый ценный и
неповторимый материал страницы находится в этой зоне или ниже? Если ниже - укажи, какой
блок нужно поднять наверх и почему он там окажется менее заменимым.

Evidence heuristic: Найди в тексте утверждения, которые звучат сильно, но не подкреплены
примерами, цифрами или источниками. Для каждого предложи один конкретный способ его
подкрепить.

Replaceability heuristic: Выбери три самых сильных, на твой взгляд, блока на странице. Для
каждого ответь: мог бы конкурент написать почти то же самое почти теми же словами? Если да -
предложи, как усилить блок.

Fallback-before-filler heuristic (для мета-полей): Если ни один факт не прошёл GIST Meta Filter -
ты уже проверил: а) факт о категории целиком? б) факт, проходящий три теста кроме
проверяемости (с доказательством в описании)? в) операционный факт о доставке/поддержке?
Если нет - сделай это, прежде чем сообщать, что факта нет.

## 8.1. ПРОМПТ ДЛЯ ПОЛНОГО ЦИКЛА STEP 8.1–8.10 ЗА ОДИН ЗАПРОС

  Собери мета-тайтл и мета-описание по Step 8 скилла для следующей страницы: [описание].

Вводные: тип страницы, 3-5 фактов о сущности, при наличии - текущие тайтлы конкурентов.

  [описание], которые потенциально могут стать основой мета-тайтла. Включи технологию или
  материал, измеримый результат, точку трения, которую снимает товар/услуга, и любое

## 8.3. ПРИЁМ "ПЯТЬ ВОПРОСОВ"

  Ответь на пять вопросов про эту сущность: [описание]. 1) Что может пойти не так при

Пример для ламината Praktik: вопрос 1 → "торцы могут набухнуть от влаги в швах" → факт

## 8.4. ПРОМПТ ДЛЯ ФИЛЬТРАЦИИ КАНДИДАТОВ ЧЕРЕЗ GIST META FILTER

<!-- source-page: 22 -->

  Проверь каждого кандидата по четырём тестам: 1) Конкретность - это named-деталь, а не
  абстрактное слово? 2) Значимость для решения - снимает реальное сомнение? 3)
  Заменяемость - может ли конкурент честно написать то же самое? 4) Проверяемость - может
  ли пользователь подтвердить факт на странице? Отбракуй кандидата, если он проваливает
  больше одного теста.

## 8.5. ПРОМПТ ДЛЯ ЗАПУСКА ЗАПАСНОГО ПОРЯДКА ДЕЙСТВИЙ

  Ни один кандидат не прошёл фильтр полностью. Примени запасной порядок действий:
  сначала проверь факт о категории или бренде целиком. Если нет - допусти кандидата,
  проходящего три теста кроме проверяемости, тогда дескрипшен должен дать проверяемое
  доказательство. Если и это не получается - используй факт о том, как товар продаётся,
  доставляется или поддерживается, но проверь его на заменяемость и проверяемость отдельно.
  Если ни один вариант не сработал - сообщи, что факта не найдено и нужна ручная проверка.

## 8.6. ПРОМПТ ДЛЯ СКОРИНГА И ВЫБОРА ФИНАЛЬНОГО ФАКТА

  Если несколько кандидатов прошли все четыре теста, отскорь их по трём измерениям от 0 до
  2: неожиданность факта, стоимость проверки, специфичность. Выбери кандидата с
  наибольшей суммой баллов, при равенстве - сначала по специфичности, потом по
  неожиданности.

## 8.7. ПРОМПТ ДЛЯ ПРОВЕРКИ КОНФЛИКТА ТАЙТЛА И ДЕСКРИПШЕНА

  Прочитай тайтл и описание как единую пару. Проверь: не повторяет ли описание тот же факт
  другими словами; не использует ли тот же маркер доказательства без новой грани. Если
  конфликт есть - перестрой описание вокруг другого факта, оставив исходный в тайтле.

## 8.8. ФИНАЛЬНАЯ ПРОВЕРКА НА ЗАМЕНЯЕМОСТЬ

  вставить своё название бренда и использовать пару почти без изменений? Если да - верни на

## ГЛАВА 9. СБОРКА МЕТА-ПОЛЕЙ ДЛЯ КАТАЛОГА (STEP 8.11)

## 9.1. ПРОМПТ ДЛЯ ПОИСКА ПЕРЕМЕННОГО АТРИБУТА ПОД ШАБЛОН

  У меня каталог из [число] карточек товаров в категории [ниша]. Вот примеры пяти-десяти
  позиций с характеристиками: [вставить]. Найди один атрибут, который варьируется по
  каталогу достаточно значимо, чтобы стать переменным слотом в шаблоне тайтла -
  конкретную, проверяемую характеристику, а не общее качественное слово.

## 9.2. ПРОМПТ ДЛЯ ВАЛИДАЦИИ ШАБЛОНА НА ТРЁХ КАРТОЧКАХ

  Собери шаблон тайтла в формате [Название] + [переменный атрибут] | [Магазин]. Примени к
  трём разным карточкам и проверь через четыре теста GIST Meta Filter. Если хотя бы одна
  проваливает больше одного теста - шаблон нужно пересобрать.

## 9.3. ПРИЁМ "АУДИТ ПОВТОРЯЕМОСТИ"

  Проверь весь список тайтлов: если один факт встречается в более чем 70% тайтлов, определи -
  это общая характеристика каталога или шаблонная лень. Если это не общая характеристика -
  предложи второй переменный слот.

## 9.4. СКВОЗНОЙ ПРИМЕР: КАТАЛОГ ЛАМИНАТА И ЛИНОЛЕУМА

Шаблон для линейки с Aqua Stop: "[Модель] Praktik + восковая защита торцов Aqua Stop |
Магазин" - проходит фильтр, факт есть только у части линейки. Шаблон для линолеума:
"[Модель] + подрезка рулона под ваш размер | Магазин" - переменный слот здесь не технология, а
услуга.

При аудите повторяемости: если "Aqua Stop" стоит в 90% тайтлов линейки Praktik - нормально,
это реальная характеристика линейки. Если "подрезка под размер" стоит в 100% тайтлов
линолеума разных брендов без разбора - сигнал, что нужен второй слот.

## ГЛАВА 11. ОСОБЫЕ СЛУЧАИ В МЕТА-ПОЛЯХ

## 11.1. ПРИЁМ ДЛЯ СТРАНИЦ ПОД СОЦСЕТИ И AI-ЦИТИРОВАНИЕ

Эта страница рассчитана на активное распространение в соцсетях и возможное цитирование в
AI-ответах, где описание может показываться без тайтла. Помести главный факт в первые 90
символов описания (кириллица), даже если это означает совпадение с фактом из тайтла - для
этой страницы это осознанное исключение из правила о конфликте.

Проверь, задан ли у страницы отдельный og:description. Если нет - предложи отдельный текст,
который может полнее раскрывать факт для карточки в соцсети.

## 11.2. ПРИЁМ ДЛЯ АКЦИОННЫХ И ВРЕМЕННЫХ ФАКТОВ

Проверь, является ли выбранный факт временным (скидка, срок акции) или стабильным. Если
единственный факт, прошедший фильтр - временный, используй его в описании, а не в тайтле,
и явно помечай: "временный факт - требуется дата пересмотра: [срок]".

## 11.3. ПРИЁМ ДЛЯ КИРИЛЛИЦЫ - БЫСТРАЯ ПРОВЕРКА ДЛИНЫ

Посчитай количество символов в тайтле и описании. Безопасный ориентир для кириллицы:
тайтл - 40-50 символов, описание десктоп - 130-145, мобильный - 90-105. Если текст
превышает границы, укажи, какая часть попадёт под обрезку, и убедись, что это не главный
факт.

## 11.4. ПРИЁМ ЭСКАЛАЦИИ К ЧЕЛОВЕКУ

Если после всех попыток, включая запасной порядок действий, ни один факт не прошёл
фильтр - не пиши тайтл и описание с абстрактными словами. Выведи явное сообщение: "Для
этой сущности не найдено факта, проходящего GIST Meta Filter ни по одному из путей.
Требуется ручная проверка" - и укажи, каких данных не хватило.

## ГЛАВА 13. РАБОТА С НЕСКОЛЬКИМИ АГЕНТАМИ/РОЛЯМИ В ОДНОЙ СЕССИИ

## 13.1. ПРИЁМ "АГЕНТ-КРИТИК"

  Теперь возьми на себя вторую роль - роль строгого критика, который проверяет соблюдение
  скилла GIST в предыдущем ответе. Ищи нарушения: остатки типового копирайтинга,
  необоснованное сохранение слабых блоков, пропущенные узлы, факты в мета-полях, не
  проходящие фильтр. Не смягчай оценку из вежливости.

  Вернись к роли автора и исправь черновик по замечаниям критика выше, начиная с самого
  критичного пункта.

## 13.2. ПРИЁМ "РАЗДЕЛЕНИЕ ПО ШАГАМ" ДЛЯ СЛОЖНЫХ СТРАНИЦ

  Сейчас работаем только с Phase [N]. Не забегай вперёд к следующим фазам - запиши идеи для
  них отдельно как "заметки на будущее", основной ответ дай только по текущей фазе.

Особенно важно для Phase 3 и Phase 7 - самых generative шагов, где модель склонна давать
поверхностные списки, если торопится к черновику.

## 13.3. МИНИ-ПРИМЕР МНОГОШАГОВОЙ СЕССИИ ДЛЯ B2B-ЛЕНДИНГА

Лендинг SaaS-продукта для оптимизации облачных расходов, аудитория - технические
директора.

Сообщение 1 (Phase 1-2): задача - убедить запросить демо; ядро - процент экономии, механизм,
отсутствие риска. Сообщение 2 (Phase 3, конкуренты): все обещают "экономию до X%" без
конкретики, никто не пишет о времени подключения. Сообщение 3 (Phase 4): выбран угол "аудит
без доступа к продакшн-инфраструктуре". Сообщение 4 (Phase 5-6): структура и черновик с этим
углом на первом экране. Сообщение 5 (агент-критик): находит общий блок "почему мы" -
отправляется на переписывание. Сообщение 6 (связка из Главы 12): сборка мета-полей на основе
угла.

Итоговая пара: тайтл "Снизьте счёт AWS на 30-50% без доступа к продакшену | CloudOpt",
описание "Бесплатный аудит без интеграции в вашу инфраструктуру. Результат виден уже в
следующем счёте. Используют 400+ команд разработки."

## ГЛАВА 14. МАССОВОЕ ПРИМЕНЕНИЕ СКИЛЛА (БАТЧИ СТРАНИЦ)

## 14.1. ПРОМПТ ДЛЯ ОБРАБОТКИ СПИСКА СТРАНИЦ ЗА ОДИН ЗАХОД

  У меня список из [N] позиций: [вставить с характеристиками]. Для каждой позиции отдельно

Признаки, что батч нужно разбить: модель повторяет один факт для разных позиций без

Правило: похожие позиции - шаблонный режим (Глава 9); разные по сути - небольшие группы
вручную.

## ГЛАВА 15. ЧАСТЫЕ ОШИБКИ ПРИМЕНЕНИЯ СКИЛЛА И КАК ИХ ИСПРАВИТЬ

## 15.1. МОДЕЛЬ "ЗАБЫЛА" СКИЛЛ В ДЛИННОЙ СЕССИИ

  Останавливаемся. Последний ответ нарушает логику скилла GIST - в нём появились типовые
  обороты без конкретных фактов. Перечитай working definitions и Step 8 (если о мета-полях) и
  переделай последний ответ.

Профилактика: используйте якорную фразу из Главы 2.4 регулярно.

## 15.2. МОДЕЛЬ ПУТАЕТ UTILITY И DISTINCTIVENESS

  Переоцени блок по Utility и Distinctiveness отдельно - это разные измерения. Блок может быть
  очень полезным, но при этом совершенно заменимым.

## 15.3. МОДЕЛЬ ПРЕДЛАГАЕТ АБСТРАКТНЫЕ ФАКТЫ ДЛЯ МЕТА-ПОЛЕЙ

  Это не факт, а абстрактное слово о качестве - оно проваливает тест на конкретность. Вернись к
  списку кандидатов и выбери фактически названную деталь. Если ни один не подходит -
  запусти запасной порядок действий.

## 15.4. МОДЕЛЬ ПРОПУСКАЕТ FALLBACK-ЦЕПОЧКУ

  Прежде чем сдаваться, пройди все три запасных варианта по порядку: факт о
  категории/бренде → факт с доказательством в описании → операционный факт. Только если
  все три не сработали - сообщи, что нужна ручная проверка.

## 15.5. МОДЕЛЬ НАРУШАЕТ CYRILLIC-SAFE ДЛИНУ

  Пересчитай длину в символах. Для кириллицы: 40-50 символов тайтл, 130-145 описание на
  десктопе, 90-105 на мобильном. Сократи текст так, чтобы главный факт остался в безопасной
  зоне.

## ГЛАВА 16. БЫСТРАЯ ДИАГНОСТИКА ПО RED-FLAG PATTERNS

## 16.1. ПРОМПТ ПОЛНОГО ПРОГОНА

Проверь прикреплённую страницу/мета-пару по полному списку red-flag patterns из скилла
GIST. По каждому флагу ответь да/нет с одной строкой доказательства из текста:
1. длинное определение в начале; 2) несколько секций говорят одно и то же; 3) FAQ забит
общими вопросами; 4) много слов, но мало различений; 5) нет сценарного мышления; 6) нет
указания "когда это не работает"; 7) нет практических критериев; 8) слабый первый экран; 9)

один факт разными словами; 15) шаблон каталога построен на общем слоте, а не на
конкретном атрибуте.
Если да - укажи конкретное место в тексте. Если красных флагов больше трёх - страница
требует переработки, а не точечных правок.

## 16.2. ОБЛЕГЧЁННАЯ ВЕРСИЯ ДЛЯ МЕТА-ПОЛЕЙ

Проверь эту пару тайтл-описание по трём ключевым красным флагам: есть ли в тайтле
абстрактное слово о качестве вместо проверяемого факта? Повторяют ли тайтл и описание
один и тот же факт разными словами? Может ли конкурент использовать эту пару почти без
изменений, просто вставив свой бренд? Если хотя бы один ответ "да" - пересобери пару.

## ПРИЛОЖЕНИЕ Г. ИНТЕГРАЦИЯ С РАБОЧИМ ПРОЦЕССОМ

## Г.1. ФОРМАТ ТЕХЗАДАНИЯ ДЛЯ КОПИРАЙТЕРА

  Собери результаты анализа/создания в формат техзадания: 1) заголовок задачи; 2) задача
  страницы одним абзацем; 3) обязательное ядро; 4) что избегать; 5) что обязательно добавить с
  пояснением; 6) порядок блоков с указанием первого самого сильного блока; 7) готовый тайтл
  и мета-описание.

## Г.2. ФОРМАТ ДЛЯ КАРТОЧКИ ЗАДАЧИ (TRELLO/ASANA/JIRA)

  Собери результат в формат карточки задачи: название (одна строка); описание (2-3
  предложения); чек-лист обязательных блоков с пометкой "сделано/не сделано"; поле
  "критерий готовности" (например: "страница проходит red-flag check - не более двух флагов").

## Г.3. ФОРМАТ CSV/TSV ДЛЯ МАССОВОГО ЭКСПОРТА В CMS

  Сведи все мета-поля в таблицу с разделителем табуляции и колонками: URL страницы,
  текущий тайтл, новый тайтл, текущее описание, новое описание, примечание (флаг ручной
  проверки/временный факт). Первая строка - заголовки. Никакого форматирования, только
  текст.

Опционально: для совместной работы над каталогом можно запросить тот же результат в
формате таблицы Google Sheets с добавленной колонкой статуса ("готов/требует
проверки/отправлено на доработку") и пустой колонкой для комментариев редактора.
