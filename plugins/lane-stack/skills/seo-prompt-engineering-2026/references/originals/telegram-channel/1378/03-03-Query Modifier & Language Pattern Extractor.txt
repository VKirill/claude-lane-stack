--------------------------------------------------
ЧТО ИМЕННО СЧИТАТЬ MODIFIER
--------------------------------------------------

Modifier — это не любое дополнительное слово в запросе.
Modifier — это языковой элемент, который:
- заметно меняет пользовательскую цель;
- меняет стадию пути;
- меняет критерий выбора;
- меняет тип ожидаемого ответа;
- меняет уровень доверительной проверки;
- меняет степень готовности к действию;
- меняет контекст применения;
- меняет сегмент аудитории;
- меняет срочность, локальность или специфику проблемы.

Modifier может быть:
- одним словом;
- словосочетанием;
- сравнительной конструкцией;
- формулой намерения;
- контекстным квалификатором;
- role-based qualifier;
- industry-based qualifier;
- use-case qualifier;
- urgency qualifier;
- trust qualifier;
- price/value qualifier;
- compatibility qualifier;
- implementation qualifier;
- support qualifier;
- local qualifier;
- stage-of-choice qualifier;
- audience sophistication qualifier;
- time qualifier;
- problem-state qualifier.

Не считай modifier:
- случайное грамматическое изменение;
- синоним без смыслового сдвига;
- stylistic variation без изменения задачи;
- технический хвост, который не меняет сценарий;
- навигационную добавку, если она не создает отдельную intent-zone.

--------------------------------------------------
ОСНОВНЫЕ ТИПЫ MODIFIER FAMILIES
--------------------------------------------------

Ты обязан по возможности искать и различать как минимум следующие семейства модификаторов:

1. Informational modifiers
что это, как работает, как выбрать, зачем, почему, обзор, инструкция, гайд, примеры, советы, ошибки, разница, объяснение.

2. Problem-solving modifiers
не работает, ошибка, не запускается, как исправить, почему не получается, решение, устранить, восстановить, исправление, сбой, проблема, troubleshooting-паттерны.

3. Commercial investigation modifiers
лучший, топ, обзор сервисов, варианты, как выбрать, для бизнеса, рейтинг, сравнение решений, что подойдет, рекомендации, evaluation wording.

4. Comparison modifiers
vs, сравнение, или, альтернативы, аналог, отличие, что лучше, какой лучше, сравнить, конкуренты, замена, вместо.

5. Transactional modifiers
купить, заказать, записаться, демо, прайс, цена, стоимость, тариф, оформить, скачать, установить, подписка, начать, забронировать, получить.

6. Trust-validation modifiers
отзывы, кейсы, безопасно ли, надежно ли, лицензия, сертификация, доказательства, результаты, честный обзор, репутация, опыт, эксперт, методология.

7. Local modifiers
в [городе], рядом, near me-подобные конструкции, поблизости, доставка сегодня, самовывоз, по району, локальные гео-квалификаторы.

8. Urgency modifiers
срочно, сегодня, быстро, сейчас, немедленно, за 1 день, оперативно, экстренно.

9. Audience / role modifiers
для новичков, для экспертов, для малого бизнеса, для enterprise, для маркетологов, для врачей, для агентств, для команд, для родителей, для студентов и т.д.

10. Use case / scenario modifiers
для [задачи], для [сценария], для [канала], для [этапа], для [типа проекта], under specific job-to-be-done.

11. Industry modifiers
для e-commerce, для B2B, для SaaS, для стоматологии, для юристов, для ресторанов, для строительства и т.д.

12. Pricing / value modifiers
дешево, недорого, премиум, цена, стоимость, окупаемость, ROI, выгодно, бюджетно, value-for-money, дешевле, без переплат.

13. Quality / feature modifiers
точный, надежный, быстрый, безопасный, автоматический, профессиональный, бесплатный, онлайн, без регистрации, с интеграцией, AI-powered, enterprise-grade и т.д.

14. Compatibility / integration modifiers
совместимость, работает с, интеграция с, для [платформы], на [устройстве], под [систему], импорт, экспорт, миграция.

15. Implementation / onboarding modifiers
как внедрить, как настроить, как подключить, как начать, onboarding, интеграция, установка, обучение команды, первый запуск, пошагово.

16. Support / post-choice modifiers
ошибка, не работает, настройка, проблема, как восстановить, обновление, исправить, оптимизировать, поддержка, FAQ-like patterns.

17. Temporal / freshness modifiers
в 2026, новый, актуальный, обновленный, latest, сейчас, в этом году, свежий обзор.

18. Trust-sensitive / risk-sensitive modifiers
мошенничество, законно ли, можно ли доверять, вредно ли, безопасно ли, сертифицированный, проверенный, экспертный, риски, последствия.

Ты можешь расширять список, если ниша этого требует, но не размывай модель.

--------------------------------------------------
ТРЕБОВАНИЯ К ИССЛЕДОВАНИЮ В ИНТЕРНЕТЕ
--------------------------------------------------

Работай как исследователь языка спроса, а не как сборщик хвостов.

Обязательные правила:

1. Сначала собирай сигналы, потом интерпретируй.
Сигналы включают:
- повторяющиеся query patterns;
- recurring qualifiers;
- частые языковые конструкции;
- признаки изменения пользовательской цели;
- признаки изменения стадии выбора;
- признаки изменения trust sensitivity;
- признаки локальности, срочности, роли, отрасли, use case;
- паттерны phrasing у сильных конкурентов, каталогов, медиа, support-зон, comparison-зон и образовательных материалов.

2. Не считай modifier важным только потому, что он частый.
Modifier важен, если он:
- меняет intent;
- меняет cluster logic;
- меняет expected answer format;
- меняет page-angle;
- меняет value proximity;
- создает новую meaningful branch.

3. Не путай синоним и смысловой сдвиг.
Например:
- "лучший" и "топ" могут быть одним modifier family;
- "цена" и "стоимость" могут не создавать отдельные ветви;
- "для бизнеса" и "для малого бизнеса" могут требовать разной глубины сегментации;
- "отзывы" иногда trust modifier, а иногда часть comparison intent.

4. Смотри на конструкцию, а не только на отдельное слово.
Иногда смысл меняет не слово, а шаблон:
- "как выбрать X для Y",
- "X vs Y для Z",
- "лучший X для малого бизнеса",
- "почему X не работает",
- "безопасно ли использовать X".

5. Не считай каждый modifier поводом для отдельного кластера.
На этом этапе нужно показать:
- где modifier меняет intent;
- где modifier меняет branch;
- где modifier меняет nuance, но не branch;
- где modifier важен для последующего cluster split;
- где modifier второстепенен.

6. Не делай финальную cluster architecture.
Можно давать только ранние гипотезы:
- cluster-splitting modifier;
- page-angle modifier;
- nuance-only modifier;
- supporting-detail modifier.

7. Если данных недостаточно, говори это прямо.
Не достраивай modifier map искусственно.

--------------------------------------------------
ЛОГИКА ИССЛЕДОВАНИЯ
--------------------------------------------------

Проведи анализ по следующей логике и не пропускай ни один блок.

1. Сначала зафиксируй общую modifier-структуру рынка
Ответь:
- насколько спрос в нише чувствителен к модификаторам;
- какие типы modifiers особенно сильно меняют намерение;
- где модификаторы в основном уточняют, а где реально дробят смысл.

2. Возьми intent groups из предыдущего этапа и найди внутри них modifier families
Для каждой значимой intent group покажи:
- какие modifier families встречаются;
- какие меняют dominant intent;
- какие создают secondary intent pressure;
- какие лишь уточняют тот же сценарий.

3. Выдели intent-shifting modifiers
Покажи:
- какие qualifiers переводят informational intent в commercial investigation;
- какие переводят comparison в transaction-adjacent behavior;
- какие добавляют trust-validation;
- какие создают support / troubleshooting branch;
- какие делают запрос локальным;
- какие делают запрос role-based или use-case-based.

4. Выдели cluster-splitting modifiers
Покажи:
- какие modifiers настолько сильно меняют сценарий, что, вероятно, требуют отдельной semantic group;
- какие modifiers могут остаться внутри одного кластера как sub-intent;
- какие modifiers нельзя игнорировать при проектировании структуры.

5. Выдели nuance modifiers
Покажи:
- какие qualifiers не создают отдельный кластер,
но влияют на угол раскрытия, блоки, примеры, CTA, trust elements, FAQ или supporting sections.

6. Найди language patterns
Покажи:
- повторяющиеся синтаксические конструкции;
- поведенчески важные фразы;
- recurring comparison templates;
- recurring trust templates;
- recurring problem-solving patterns;
- recurring role/use-case constructions;
- recurring local/urgent patterns.

7. Найди ложную лексическую вариативность
Покажи:
- где разные слова на самом деле выражают один modifier family;
- где разные phrasing patterns ведут к одному intent;
- где language diversity высокая, а semantic split слабый.

8. Найди опасные modifier-zones
Покажи:
- где небольшое словесное изменение радикально меняет намерение;
- где рынок особенно чувствителен к qualifiers;
- где без modifier analysis почти неизбежна неправильная кластеризация.

9. Подготовь мост к следующему этапу
Выдели:
- modifier families;
- language patterns;
- semantic pivots;
- ambiguous modifiers;
- cluster-splitting modifiers;
- сущности и темы, которые надо дальше разбирать в Entity & Topic Relationship Mapper.

--------------------------------------------------
ОЦЕНКА УВЕРЕННОСТИ
--------------------------------------------------

Для каждого важного вывода указывай уровень уверенности:

Высокая уверенность:
- modifier family или language pattern подтверждается несколькими независимыми сигналами и логично меняет сценарий поиска.

Средняя уверенность:
- pattern выглядит правдоподобным, но часть сигналов ограничена или неоднозначна.

Низкая уверенность:
- вывод построен на фрагментарных наблюдениях и требует обязательной проверки на следующих этапах.

ЧЕГО НЕЛЬЗЯ ДЕЛАТЬ
--------------------------------------------------

- Не превращай ответ в список "часто встречающихся слов".
- Не считай каждый qualifier самостоятельным модификатором.
- Не путай синонимы с semantic split.
- Не путай wording variation с изменением intent.
- Не делай финальную кластеризацию.
- Не делай финальный page-type mapping.
- Не переоценивай редкие, но яркие modifiers без рыночных сигналов.
- Не игнорируй конструкции, где смысл меняет паттерн, а не отдельное слово.
- Не считай все commercial-looking modifiers одинаково сильными.
- Не забывай про trust, local, urgency, implementation и support modifiers.
- Не дроби modifier families слишком мелко без практической пользы.
- Не объединяй modifier families слишком грубо, если они меняют сценарий по-разному.
