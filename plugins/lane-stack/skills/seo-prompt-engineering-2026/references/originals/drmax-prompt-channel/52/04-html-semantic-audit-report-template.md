# Шаблон выходного отчёта: production-формат аудита HTML-страницы на семантическую верстку

## Назначение

Этот шаблон нужен для того, чтобы любой LLM выдавал результат аудита HTML-страницы в одном и том же формате: стабильно, предсказуемо, удобно для QA, удобно для постановки задач разработке, удобно для сравнения разных страниц между собой и удобно для последующей автоматизации.

Шаблон рассчитан на анализ уже отрендеренного HTML-кода страницы и должен использоваться вместе с:

- файлом общей логики семантической HTML-разметки;
- файлом логики по типам страниц;
- супер-промптом аудита HTML.

Этот документ не объясняет теорию семантической верстки заново. Он задает строгий output contract: как именно LLM должен оформлять результаты анализа.

---

## Принцип использования

LLM должен:

1. Принять HTML.
2. Определить тип страницы.
3. Выявить основную сущность и основной интент.
4. Проверить семантическую структуру.
5. Найти semantic gaps.
6. Найти быстрые и глубокие улучшения.
7. Выдать результат строго по этому шаблону.

Если каких-то данных в HTML недостаточно, модель должна явно писать, что вывод предположительный.

---

## Общие правила output-формата

### Правило 1. Всегда использовать одинаковый порядок блоков

Даже если на странице мало данных, структура ответа не должна ломаться. Допускается пометка `Недостаточно данных`, но не пропуск обязательных секций.

### Правило 2. Никакой воды

Каждый блок отчета должен содержать:

- конкретное наблюдение,
- его значение для SEO/LLM/AI-citation,
- практический вывод.

### Правило 3. Никаких абстрактных рекомендаций

Запрещены советы уровня:

- “улучшите семантику”;
- “добавьте структуру”;
- “поработайте над accessibility”;
- “оптимизируйте HTML”.

Каждая рекомендация должна привязываться к конкретному HTML-блоку и конкретному тегу или паттерну.

### Правило 4. Приоритет practical implementation

Отчет должен быть полезен для:

- SEO-специалиста,
- frontend-разработчика,
- тимлида,
- QA,
- контентной команды,
- автоматизированного пайплайна анализа.

### Правило 5. Если блок уже размечен хорошо — это тоже фиксировать

Шаблон нужен не только для поиска ошибок, но и для фиксации сильных сторон текущего HTML.

## Строгий шаблон отчета

Ниже — формат, который LLM должен воспроизводить без изменений логики и порядка секций.

---

# 1. Служебный блок

## 1.1. Идентификация страницы

- URL: 
- Title: 
- H1: 
- Предполагаемый тип страницы: 
- Вторичный тип страницы, если есть: 
- Уровень уверенности определения типа: высокий / средний / низкий

## 1.2. Основание классификации

Кратко перечислить сигналы, по которым определен тип страницы:

- наличие одной доминирующей сущности;
- наличие листинга;
- наличие товарных карточек;
- наличие формы/калькулятора;
- наличие FAQ;
- наличие табличного сравнения;
- наличие author/company/trust-блоков;
- наличие хронологической или справочной структуры.

---

# 2. Executive summary

Дать короткий сводный вывод в 4–8 предложениях.

Что обязательно отразить:

- общее качество семантической верстки;
- есть ли сильные structural signals;
- есть ли критичные semantic gaps;
- насколько хорошо выражена основная сущность страницы;
- насколько удобно извлекать факты LLM;
- насколько реалистичны улучшения без полного рефакторинга.

Формат:

- 1 абзац или 4–6 буллетов.

---

# 3. Primary intent и primary entity

## 3.1. Основной интент страницы

Ответить одной фразой:

- что страница должна продавать, объяснять, сравнивать, подтверждать или представлять.

## 3.2. Основная сущность страницы

Указать:

- кто или что является главной сущностью;
- есть ли вторичные сущности;
- не конкурируют ли между собой несколько сущностей.

## 3.3. Ключевые факты, которые должны быть легко извлекаемы

Список 3–10 фактов, которые должны считываться максимально легко.

Примеры:

- название товара;
- тип услуги;
- цена или цена от;
- условия доставки;
- ограничения;
- срок;
- совместимость;
- автор;
- дата публикации;
- юридический статус;
- должность эксперта.

# 5. Что сделано хорошо

Секция обязательна даже при слабом HTML.

# 7. Подробный аудит по semantic dimensions

Эта секция обязательна. Она стандартизирует глубокий разбор.

## 7.1. Document landmarks

Проверить и описать:

- `html[lang]`
- `header`
- `nav`
- `main`
- `aside`
- `footer`

Формат:

| Элемент | Статус | Комментарий | Практический вывод |
|---|---|---|---|

## 7.2. Границы сущностей

Проверить:

- есть ли `article` там, где есть самостоятельные сущности;
- отделены ли карточки, отзывы, кейсы, вакансии, FAQ-элементы, видео, документы;
- нет ли смешения нескольких сущностей в одном контейнере.

Формат:

| Объект анализа | Текущее состояние | Проблема / сила | Рекомендация |
|---|---|---|---|

## 7.3. Тематическая структура

Проверить:

- иерархию `h1-h6`;
- наличие `section`;
- корректность заголовков секций;
- есть ли retrieval-friendly headings.

Формат:

| Блок | Текущая разметка | Оценка | Что улучшить |
|---|---|---|---|

## 7.4. Факты и атрибуты

Проверить:

- используется ли `dl` для пар “атрибут–значение”;
- используется ли `table` для табличных данных;
- используются ли `ul/ol` для списочной информации;
- есть ли `time` для дат и сроков;
- есть ли `data`, где это полезно;
- не передаются ли факты как хаотичный текст.

Формат:

| Тип факта | Текущее состояние | Потенциальный semantic upgrade | Ожидаемый эффект |
|---|---|---|---|

## 7.5. Медиа и подписи

Проверить:

- есть ли `figure/figcaption`;
- есть ли понятные `alt`;
- есть ли текстовое дублирование важных визуальных фактов.

Формат:

| Медиа-блок | Текущее состояние | Проблема / сила | Что улучшить |
|---|---|---|---|

## 7.6. Интерактив и формы

Проверить:

- корректность `form`, `label`, `fieldset`, `legend`, `button`, `output`;
- не перепутаны ли `a` и `button`;
- есть ли semantic grouping в фильтрах, калькуляторах и checkout-сценариях.

Формат:

| Интерактивный блок | Текущее состояние | Проблема / сила | Рекомендация |
|---|---|---|---|

## 7.7. Trust / E-E-A-T / identity

Проверить:

- как размечены контакты, авторы, документы, отзывы, кейсы, компания, реквизиты, команда;
- есть ли `address`, `article`, `figure`, `dl`, `time`, `blockquote`, где они уместны.

Формат:

| Блок доверия | Текущее состояние | Потенциал усиления | Рекомендация |
|---|---|---|---|

## 7.8. AI-extractability и citation-readiness

Проверить:

- есть ли citation-friendly блоки;
- есть ли top facts panel;
- есть ли chunk-friendly секции;
- отделен ли semantic noise;
- не мешает ли DOM-структура быстрой суммаризации.

Формат:

| Параметр | Оценка | Комментарий | Что улучшить |
|---|---|---|---|

# 8. Упущенные возможности

Это отдельная секция для advanced improvements.

Сюда выносятся не грубые ошибки, а потенциал роста.

Формат:

- 5–15 пунктов.
- Каждый пункт должен быть в формате:
  - Возможность
  - Где применить
  - Как реализовать
  - Какой эффект для ранжирования / LLM-extraction / AI-citation

Примеры типов возможностей:

- top facts panel через `dl`;
- citation zone для ограничений;
- nested `article` для отзывов;
- `table` вместо div-grid;
- `details/summary` для вторичных FAQ-блоков;
- `figure/figcaption` для сертификатов;
- `time` для условий акции;
- page-nav для гайда;
- `fieldset/legend` для фильтров.

# 9. Практические рекомендации по внедрению

Главная production-секция.

Формат таблицы:

| Блок страницы | Что есть сейчас | Что сделать | HTML-паттерн | Приоритет | Сложность | Ожидаемый эффект |
|---|---|---|---|---|---|---|

Правила:

- Рекомендации формулировать как backlog-ready задачи.
- Не писать “улучшить семантику”.
- Писать в терминах конкретной доразметки.

Хорошие формулировки:

- Обернуть карточки товаров листинга в `article`.
- Перевести блок характеристик из двух div-колонок в `dl > dt + dd`.
- Перестроить блок сравнения моделей в `table` с `caption`, `thead`, `th`, `td`.
- Добавить `time[datetime]` к срокам акции и дате обновления.
- Разделить hero, facts и related-блоки через `section`/`aside`.

# 10. Лучшие улучшения именно для этого типа страницы

Это page-type specific секция.

Нужно дать 5–10 наиболее ценных улучшений именно для типа страницы, который был определен.

Формат:

| Улучшение | Почему это особенно важно для этого типа страницы | Практика внедрения |
|---|---|---|

Примеры:

- Для карточки товара: `dl` для specs, `article` для reviews, `time` для условий акции.
- Для услуги: `dl` для формата работ, `ol` для этапов, отдельная секция ограничений.
- Для FAQ: answer-first блоки, `details` для компактных ответов, `article` для длинных ответов.
- Для профиля автора: `dl` для квалификации и ролей, `section` для публикаций и специализаций.

# 14. Финальный короткий вывод

Закрывающий блок в 3–6 предложениях.

Нужно ответить:

- какова главная семантическая проблема страницы;
- какой один апгрейд даст наибольший эффект;
- насколько легко добиться заметного улучшения без тотального рефакторинга.

## Жесткие требования к качеству output

LLM, использующий этот шаблон, обязан:

- не пропускать обязательные секции;
- не менять порядок секций;
- не заменять таблицы длинными абзацами там, где нужен structured output;
- не давать общие рекомендации без привязки к HTML;
- не путать SEO-семантику, accessibility и microdata;
- не придумывать отсутствующий контент;
- явно маркировать предположения;
- писать так, чтобы вывод можно было отдать в разработку без дополнительной расшифровки.

## Рекомендуемый короткий системный instruction для подключения шаблона

Используй этот файл как строгий output contract. Анализируй HTML свободно, но оформляй финальный результат только в структуре этого шаблона. Не меняй порядок разделов. Не пропускай обязательные секции. Все рекомендации формулируй как внедряемые задачи для существующего HTML. Если данных мало, явно указывай предположительность выводов, но структуру отчета сохраняй полностью.
