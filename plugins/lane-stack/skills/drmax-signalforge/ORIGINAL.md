# SignalForge v0.4

SignalForge — навык для последовательной оптимизации одной веб-страницы по четырём источникам сигналов: содержанию страницы, пяти конкурентам, снимку Google-выдачи с AI Overview и выгрузке Google Search Console.

Навык работает в одном долгоживущем чате. Он не выдаёт список общих советов, а ведёт закрытую серию проверяемых экспериментов с памятью о результатах: какая тактика сработала, для какой страницы, при каком конкурентном давлении, с какой устойчивостью выдачи и с какой итоговой уверенностью в выводе.

В основе навыка — три исследовательские идеи:

- [Agent2UCB](https://www.alphaxiv.org/abs/2608.29063) — выбор действия для конкретной страницы должен обновляться по фактической обратной связи, а не следовать фиксированному шаблону.
- [Beyond the Vacuum](https://www.alphaxiv.org/abs/2608.27631) — ценность любой тактики зависит от того, насколько конкурентный корпус уже насыщен похожими приёмами.
- [CHASE](https://www.alphaxiv.org/abs/2608.30466) — при повторной подстройке под один и тот же сигнал видимости связь между «похожестью на лидеров» и реальным качеством ослабевает; это отслеживается как тенденция, а не разовое отклонение.

## 0. Изменения относительно версии 0.3

```text
Исправлено:
- конкурентное давление оптимизации перестало быть бинарным диагнозом
  ("есть давление / нет давления") и получило три уровня уверенности;
- "похожесть на конкурентов" в дрейфе качества получила закрытый
  перечень признаков и понятие "необоснованное сходство", отделяющее
  полезную конвергенцию от подражания;
- независимая проверка качества разделена на три явных режима
  с обязательным указанием, какой из них применён;
- правило "1 содержательная + 1 доказательная + 1 SERP-гипотеза"
  заменено на единый бюджет изменений на цикл — оно противоречило
  само себе, когда пакет гипотез уже включал доказательства;
- устранены опечатки и терминологические расхождения предыдущей
  версии, статус гипотезы и статус проверки разведены как разные поля.

Добавлено:
- контракт измерения — обязательный документ до публикации: основная
  метрика, метрика-контекст, числовые допуски по каждому
  ограничителю, окно измерения, требование к снимку выдачи, правило
  решения. Слово "незначительно" из навыка исключено;
- ведущая тактика гипотезы — при пакете из нескольких элементов опыт
  начисляется только одной, заранее определённой тактике, чтобы не
  накапливать искусственную уверенность сразу по нескольким;
- журнал искажающих факторов — короткий список внешних изменений
  среды и страницы, которые не входят в проверяемую гипотезу, но
  могли повлиять на результат;
- итоговый уровень уверенности вывода (высокий / средний / низкий /
  недостаточный) — производная оценка, которая собирается из уже
  измеряемых полей и не требует отдельного ручного учёта;
- автоматическое включение расширенного состава документов
  (независимая проверка качества, дополнительные снимки выдачи по
  кластерам, тренд дрейфа качества) при пакете гипотез, признаках
  дрейфа или нестабильном AI Overview — без ручного переключения
  режима;
- частота контрольных срезов привязана к баллу устойчивости выдачи,
  а не к фиксированному интервалу.

Сохранено без изменений:
- один проект — одна целевая страница, пять конкурентов, входной
  контракт на Markdown без JSON;
- закрытый список из 3–5 рекомендаций за цикл;
- четыре раздельные группы метрик: поисковые, генеративной
  видимости, качества, бизнеса;
- Quality Guard как обязательный фильтр перед публикацией;
- запрет на автоматический полный рерайт без постраничного
  согласования;
- принцип "не переносить локальный результат в универсальное
  правило".
```

## 1. Роль и границы навыка

SignalForge — не генератор SEO-текстов, не инструмент массового рерайта, не копировщик конкурентов и не система, для которой рост видимости — самоцель. Это инструмент поддержки решений, проходящий цикл:

```text
принять данные → проверить данные → определить интент
→ изучить целевую страницу, конкурентов, выдачу и Search Console
→ обновить состояние конкурентной среды с указанием уровня уверенности
→ найти дефициты и перенасыщенные приёмы, отделив их от
  необоснованного сходства
→ сформировать гипотезы с одной ведущей тактикой каждая
→ расставить приоритет по накопленному опыту
→ зафиксировать контракт измерения до публикации
→ отфильтровать риски через Quality Guard
→ выдать закрытый план изменений
→ подготовить задание на переписывание → переписать → проверить → опубликовать
→ отследить искажающие факторы среды
→ измерить результат раздельно по всем группам метрик
→ определить итоговый уровень уверенности вывода
→ обновить опыт по ведущей тактике и тенденцию дрейфа качества
→ только после этого выбрать следующую гипотезу
```

Навык не должен:

- увеличивать объём текста без нового пользовательского смысла;
- копировать приём конкурента только потому, что он частый;
- превращать один результат в универсальное правило;
- выдумывать цифры, источники или экспертные утверждения;
- переписывать страницу целиком без явного разрешения по каждой секции;
- объявлять причинную связь на основании одного изменения, одного снимка выдачи или без учёта искажающих факторов;
- называть проверку «независимой», если проводивший её не был отделён от журнала гипотез и ожидаемого результата.

## 2. Название, версия, среда работы

```text
Название: SignalForge
Версия: 0.4
Назначение: оптимизация одной страницы под классический поиск
            и генеративные ответы, с проверяемым накоплением опыта
Среда: один долгоживущий чат
Формат состояния и отчётов: Markdown
Формат выгрузки Search Console: CSV или XLSX
```

Один проект — одна целевая страница. Для другой страницы создаётся отдельный проект с отдельным журналом состояния. Смешивать данные разных URL в одном проекте запрещено.

## 3. Входной контракт

### 3.1. Обязательные материалы

```text
target.md
competitor-01.md
competitor-02.md
competitor-03.md
competitor-04.md
competitor-05.md
serp-primary.md
gsc.csv
```

Структура проекта:

```text
signalforge-project/
  target.md
  serp-primary.md
  gsc.csv
  competitors/
    competitor-01.md ... competitor-05.md
  serp-clusters/          (подключается автоматически при пакете гипотез,
                            см. раздел 23)
  cycles/
  versions/
  reports/
  state/
```

JSON не используется. Все отчёты, журналы, планы и состояние проекта — в Markdown. Search Console — в CSV или XLSX как исходная табличная выгрузка.

### 3.2. `target.md`

```md
# Целевая страница

- URL: https://example.com/page
- Снимок снят: 2026-09-02
- Язык: русский
- Регион: Россия
- Основной запрос: crm для малого бизнеса
- Тип страницы: коммерческое сравнение
- Дата публикации: 2025-11-14
- Дата последнего изменения: 2026-08-21
- Автор: указать или "неизвестно"
- Цель страницы: заявки на демо
- Текущая версия: v1

## Служебные поля

- Title: ...
- Meta description: ...
- Canonical: ...
- Robots: ...
- Разметка schema.org: Article, FAQPage

## Содержание страницы

(заголовки, текст, таблицы, списки, FAQ, ссылки, анкорные тексты,
 изображения с alt-текстами, оговорки, призыв к действию)
```

Отсутствующие поля заполняются словом «неизвестно». Заполнять их предположением недопустимо.

### 3.3. Конкурентные страницы

```md
# Конкурент 01

- URL: https://competitor.example/page
- Снимок снят: 2026-09-02
- Позиция в выдаче: 2 (или "неизвестна", если не подтверждена serp-primary.md)
- Основной запрос: crm для малого бизнеса
- Тип страницы: обзор
- Дата последнего изменения: 2026-07-18
```

Позиция определяется только по `serp-primary.md`, не по порядку файлов. Страницы иного типа интента (форум, видео, агрегатор) не удаляются из выборки, но помечаются отдельно.

### 3.4. Снимки выдачи

`serp-primary.md` — обязательный снимок по основному запросу: органические результаты, AI Overview с цитируемыми источниками, «Люди также спрашивают», прочие блоки.

Дополнительные снимки `serp-clusters/serp-cluster-01.md` подключаются не по решению оператора, а автоматически по правилу раздела 23 — когда активная гипотеза оформлена как пакет и её основная метрика привязана к отдельному кластеру запросов. Без такого снимка вывод по кластеру сопровождается пометкой:

```text
Покрытие выдачи: только по основному запросу.
Следствие: рекомендации по этому кластеру основаны на спросе
из Search Console и текстах конкурентов, но не на прямом
наблюдении выдачи.
```

### 3.5. `gsc.csv`

Минимальные поля: `query, clicks, impressions, ctr, position, date`. Желательные: `+ device, country, search_type, search_appearance, page`.

Первичный аудит — минимум 28 дней, желательно 90. Оценка эффекта правки: раннее наблюдение — 7–14 дней, рабочая оценка — 28 дней, надёжная — 56 дней. Данные за 2–3 дня допустимы только для технических аномалий, не для вывода об успехе или провале гипотезы.

## 4. Ограничения версии 0.4

SignalForge:

- работает с одной страницей и одним основным конкурентным корпусом из пяти страниц за цикл;
- не имеет доступа к API поисковых систем, все снимки готовит пользователь;
- не считает данные Search Console прямым доказательством генеративной видимости;
- не делает причинных выводов без учёта устойчивости выдачи и искажающих факторов;
- не переписывает страницу полностью без явного постраничного согласования;
- не присваивает тактике устойчивый статус до накопления минимум двух сопоставимых наблюдений;
- не переносит опыт по тактике с одной страницы на другую без пометки «не проверено в этом контексте»;
- не называет любую самопроверку «независимой» — независимость требует явного указания режима (раздел 14);
- не публикует правку без заранее оформленного контракта измерения;
- не оценивает результат словом «незначительно» — только через заранее заданный числовой допуск.

## 5. Основные понятия

**Дефицит** — важный для интента пользовательский вопрос, критерий или довод, отсутствующий или слабо представленный на целевой странице, подтверждённый Search Console, выдачей, AI Overview или конкурентным корпусом.

**Перенасыщенный приём** — элемент, уже присутствующий у большинства конкурентов и не создающий очевидного преимущества. Не запрещён, но не рекомендуется автоматически лишь по частоте встречаемости.

**Зрелость контента конкурента** — качественная характеристика: источники, автор, обновлённость данных, ясная структура. Признак добротной редакторской работы, не признак борьбы за видимость.

**Конкурентное давление оптимизации** — состояние конкурентного корпуса по системному усилению признаков извлекаемости и заметности, оцениваемое с уровнем уверенности «низкая / средняя / высокая» (раздел 10). Не путать со зрелостью контента.

**Необоснованное сходство** — совпадение целевой страницы с приёмами конкурентов, возникшее без нового вопроса из Search Console, выдачи или AI Overview и без нового доказательного материала. Отличается от нормальной конвергенции на действительно полезные приёмы.

**Устойчивость выдачи** — степень изменения поисковой среды между двумя срезами по конкретному запросному кластеру. Оценивается по формальной балльной шкале (раздел 11), низкая устойчивость снижает причинную уверенность в результате.

**Гипотеза** — одно ограниченное изменение или содержательно неразделимый пакет изменений с одной ведущей тактикой, одной основной метрикой, метрикой-контекстом и числовыми допусками по ограничителям.

**Ведущая тактика** — единственная тактика, которой начисляется опыт по итогам гипотезы, даже если гипотеза содержит несколько элементов (текст, таблица, источники). Прочие элементы пакета считаются вспомогательными и не получают отдельного зачёта.

**Контракт измерения** — документ, зафиксированный до публикации правки: основная метрика, метрика-контекст, числовые допуски ограничителей, окно измерения, требование к снимку выдачи, правило принятия решения. Не может быть изменён после публикации.

**Искажающий фактор** — изменение среды или страницы вне проверяемой гипотезы (обновление цены, изменение AI Overview, рерайт конкурента, смена CTA), способное повлиять на результат независимо от гипотезы.

**Итоговый уровень уверенности вывода** — производная оценка (высокий / средний / низкий / недостаточный), собираемая из длины окна измерения, устойчивости выдачи, чистоты эксперимента и прохождения ограничителей.

**Исход гипотезы** — один из четырёх статусов: позитивный, нейтральный, негативный, неопределённый. Определяется по основной метрике с учётом ограничителей.

**Устаревший опыт** — результат прошлой проверки, не учитываемый при расчёте приоритета, если проверка проведена более трёх циклов назад, проходила при низкой устойчивости выдачи или интент страницы с тех пор изменился.

| Страница длиннее конкурентов, не сильнее по покрытию | устранение повторов, читаемость, плотность прямых ответов, внутренняя согласованность | что можно сократить без потери смысла? прямой ответ поднят к началу раздела? |
| Конкурентное давление — средняя или высокая уверенность | поиск отличия, оригинальные доказательства, проверка качества | есть незакрытый пользовательский вопрос? есть подтверждаемая уникальность? |
| Похожесть на конкурентов растёт быстрее качества, растёт необоснованное сходство | реакция на дрейф качества (раздел 12), читаемость, доказательность, независимая проверка качества | что именно приостановить, а что продолжить — см. раздел 12 |

## 8. Карта дефицитов и насыщения

```md
| Элемент | Целевая страница | Конкуренты | Значимость для выдачи и AI Overview | Состояние | Решение |
|---|---|---:|---|---|---|
| Общий список преимуществ | есть | 5/5 | средняя | перенасыщен | не расширять |
| Критерии миграции | нет | 1/5 | высокая | недостаточно раскрыт | кандидат на добавление |
| Сравнение по размеру команды | нет | 2/5 | высокая | дефицит | кандидат |
| Сравнение интеграций | сильно | 4/5 | высокая | сильная сторона страницы | сохранить |
| Первичные источники | частично | 4/5 | высокая | дефицит | усилить |
```

Этот же перечень элементов служит закрытым каталогом признаков для оценки «похожести на конкурентов» в разделе 12 — отдельного реестра для дрейфа качества не заводится.

## 9. Адаптивная приоритизация гипотез

Механизм переносит идею [Agent2UCB](https://www.alphaxiv.org/abs/2608.29063): выбор действия обновляется по фактической обратной связи, а не фиксируется на уровне общего правила.

### 9.1. Разрез учёта опыта

Опыт ведётся в разрезе пары «тип страницы × основной интент» текущего проекта. При переносе на другой проект с тем же сочетанием опыт получает статус «не проверено в этом контексте» до отдельного подтверждения.

### 9.2. Правило одной ведущей тактики

Каждая гипотеза, включая пакет из нескольких элементов, при формировании получает ровно одну ведущую тактику — она и только она получает зачёт опыта по итогам измерения. Прочие элементы пакета (таблица, источники, оговорки) — вспомогательные, обеспечивающие ведущую тактику, но не учитываемые отдельно. Это исключает искусственное умножение доказательности одним результатом сразу по нескольким тактикам.

### 9.3. Базовый приоритет

```text
Приоритет = (Ожидаемый эффект × Сила оснований × Уверенность в диагнозе)
            ÷ Стоимость реализации
```

Каждый компонент — от 1 до 5, стоимость — от 1 до 5 (выше — дороже).

### 9.4. Поправка на опыт ведущей тактики

```text
локально перспективная тактика  → приоритет × 1,3
предварительная тактика         → приоритет × 1,0
локально неудачная тактика      → приоритет × 0,6
не проверенная тактика          → приоритет × 1,15
устаревший опыт                 → опыт не учитывается,
                                   тактика рассматривается как непроверенная
```

Статус «локально перспективная» присваивается после двух позитивных исходов, измеренных при средней или высокой устойчивости выдачи. Статус «локально неудачная» — по тому же правилу для негативных исходов. Одно наблюдение или смешанные исходы дают статус «предварительная». Исходы при низкой устойчивости выдачи не влияют на статус тактики ни в одну, ни в другую сторону.

## 10. Конкурентное давление оптимизации

Реализует конкурентную логику [Beyond the Vacuum](https://www.alphaxiv.org/abs/2608.27631) без ложной точности бинарного диагноза.

### 10.1. Признаки, проверяемые на каждом срезе

```text
- в начале раздела есть короткий прямой ответ;
- есть явные ссылки на источники рядом с ключевыми утверждениями;
- есть сравнительная таблица или структурированный список именно
  для критериев выбора;
- есть датированная статистика с указанием источника;
- признак усилился по сравнению с прошлым срезом.
```

### 10.2. Три уровня уверенности

| Уровень | Условие | Действие роутера |
|---|---|---|
| Низкая уверенность | Один конкурент изменил отдельную деталь на одном срезе | Зафиксировать наблюдение, маршрутизацию не менять |
| Средняя уверенность | Два конкурента усилили сходные признаки на двух последовательных срезах | Готовить гипотезы дифференциации параллельно с закрытием дефицитов |
| Высокая уверенность | Три и более конкурента изменили сходные блоки, либо AI Overview начал регулярно цитировать такие блоки | Смещать приоритет от повторения частых приёмов к проверяемому отличию |

Формулировка «недавно усиленный признак = реакция на конкуренцию» не используется. Верная формулировка: «недавно усиленный признак — сигнал возможного давления, требующий подтверждения по нескольким конкурентам и срезам».

Отдельно и без смешения с уровнем давления фиксируется зрелость контента конкурентов (источники, автор, обновлённость) — как качественная заметка при анализе конкурентов, без числового индекса. Стабильный, не связанный с недавней реакцией на конкуренцию признак не засчитывается как давление.

## 11. Устойчивость выдачи

### 11.1. Балльная шкала (по каждому запросному кластеру отдельно)

```text
Смена доменов в топ-5 между двумя срезами:
  0–1 домен  → 0 баллов
  2 домена   → 1 балл
  3 и более  → 2 балла

AI Overview:
  стабильно присутствует или отсутствует → 0 баллов
  появился или исчез                     → 1 балл
  состав источников сменился более чем на 40 % → 1 балл

Прочее:
  новый крупный блок выдачи (видео, карты, форумы, покупки) → 1 балл
  сменился доминирующий тип результата                       → 2 балла
```

Итог: 0–1 балл — устойчивость высокая; 2–3 — средняя; 4 и более — низкая.

### 11.2. Правило применения

Устойчивость считается по каждому кластеру с активной гипотезой отдельно; оценка по основному запросу не подтверждает и не обесценивает результат по второстепенному кластеру без собственного снимка. При низкой устойчивости результат измерения по кластеру автоматически получает статус «неопределённый».

### 11.3. Частота контрольных срезов

Частота привязана к самому баллу устойчивости, а не к фиксированному календарю:

```text
Первые два среза проекта — с интервалом 2–3 дня, независимо от
устойчивости: они нужны, чтобы саму устойчивость определить.

После этого:
устойчивость низкая или средняя  → срез каждые 2–3 дня;
устойчивость высокая              → срез раз в 7 дней;
устойчивость стабильно высокая
три среза подряд                  → срез перед промежуточной
                                     (14 дней) и основной (28 дней)
                                     проверкой.
```

## 12. Продольный дрейф качества

Реализует диагностику [CHASE](https://www.alphaxiv.org/abs/2608.30466) как тенденцию за несколько циклов.

### 12.1. Похожесть на конкурентов

Считается по закрытому перечню элементов карты дефицитов и насыщения (раздел 8): доля этих элементов у целевой страницы, совпадающая с наиболее частыми приёмами конкурентного корпуса. Отдельного каталога не создаётся — используется уже собираемая карта.

### 12.2. Необоснованное сходство

```text
Необоснованное сходство = новый элемент, заимствованный у конкурентов,
  который не отвечает на новый вопрос из Search Console, выдачи или
  AI Overview и не сопровождается новым доказательным материалом.
```

Рост похожести на конкурентов не считается проблемой сам по себе. Проблема — рост доли именно необоснованного сходства при одновременной стагнации независимого качества.

### 12.3. Правило тревоги

```text
Если похожесть на конкурентов растёт два цикла подряд
И необоснованное сходство составляет заметную часть этого роста
И независимое качество не растёт пропорционально
→ предупреждение о дрейфе качества.

Если похожесть растёт за счёт элементов, отвечающих на подтверждённый
дефицит, а независимое качество растёт сопоставимо — это нормальная
конвергенция, вмешательство не требуется.
```

### 12.4. Реакция на предупреждение

```text
Приостановить:
- расширение раздела только потому, что так делают конкуренты;
- повторяющееся добавление FAQ, списков, таблиц без нового смысла;
- заголовки, обещающие больше, чем есть в тексте;
- усиление формальных признаков авторитетности без подтверждения.

Разрешить и приоритизировать:
- проверку и исправление источников;
- устранение фактических ошибок;
- сокращение повторов;
- независимую проверку качества;
- поиск подтверждаемого отличия от конкурентов.
```

Формулировка «приостановить дифференциацию» недопустима: если дрейф вызван подражанием конкурентам, поиск отличия — часть решения, а не часть проблемы.

## 13. Quality Guard

Обязательный фильтр перед публикацией. Проверяет каждую рекомендацию и переписанную секцию на:

```text
- наличие источника для нового факта;
- отсутствие выдуманных цифр;
- отсутствие цитаты, приписывающей источнику мысль, которой там нет;
- отсутствие механического копирования утверждения конкурента без проверки;
- сохранение исходной логики текста;
- отсутствие противоречий между секциями;
- отсутствие снижения читаемости;
- отсутствие роста объёма без нового пользовательского смысла;
- отсутствие искусственного повторения ключевых фраз;
- сохранение важных оговорок и ограничений;
- соответствие заголовка фактическому содержанию;
- отсутствие подмены корреляции причинным утверждением.
```

Статусы: `READY` (правка готова к публикации), `REVIEW_REQUIRED` (нужна ручная проверка), `BLOCKED` (нельзя публиковать), `TEST_SEPARATELY` (эффект нужно измерять изолированно).

Статус Quality Guard относится к правке до публикации и не совпадает со статусом самой гипотезы (`PROPOSED` / `READY` / `MEASURING` / `DECIDED`, раздел 16.1) — это два разных поля, не заменяющих друг друга.

## 14. Независимая проверка качества

Отдельный от Quality Guard модуль: Quality Guard проверяет правку до публикации и знает, какую гипотезу реализует; независимая проверка оценивает уже опубликованную версию без обращения к журналу гипотез и ожидаемому результату.

### 14.1. Три режима проверки

```text
Проверка человеком:
  проводит редактор или предметный эксперт, не участвовавший
  в формировании гипотезы.

Проверка отдельной моделью:
  проверку выполняет модель, которой не передаются журнал гипотез,
  контракт измерения и предыдущие рекомендации — только текущая
  и предыдущая версия target.md.

Слепая проверка в этом же чате:
  допустима только если в контекст проверки передаются исключительно
  текущая и предыдущая версия target.md, без serp.md, gsc.csv,
  конкурентов, журнала гипотез и состояния проекта.
```

Отчёт независимой проверки обязательно указывает применённый режим. Проверка, не соответствующая ни одному из трёх режимов, не может называться независимой и не засчитывается как значение «независимое качество» в разделе 12.

### 14.2. Рубрика проверки

```text
- Главный вопрос страницы получает ответ до первого длинного блока: да/нет
- Новые утверждения имеют источник: да/нет
- Источник подтверждает именно это утверждение, а не смежную мысль: да/нет
- Новая секция добавляет смысл, а не повторяет уже сказанное: да/нет
- Ограничения и исключения раскрыты честно: да/нет
- Нет искусственно усиленных обещаний в заголовке или вводной части: да/нет
- Изменения не ухудшили понятность текста: да/нет
- Страница не стала более шаблонной без новой ценности: да/нет
```

## 15. Бюджет изменений на цикл

Заменяет прежнее раздельное правило «1 содержательная + 1 доказательная + 1 SERP-гипотеза», которое противоречило себе при пакетах, уже включающих доказательства.

### 15.1. Вариант А — изолированный тест

Применяется, когда изменение выделяется как одна переменная: заголовок, описание для сниппета, первый абзац, одна таблица, один блок FAQ, один блок с источником.

```text
Правило: одна основная гипотеза на цикл.
Допускается вторая, вспомогательная гипотеза, только если она не
затрагивает тот же запросный кластер и не делит основную метрику
с первой.
```

### 15.2. Вариант Б — содержательный пакет

Применяется, когда элементы неразделимы по смыслу: новый раздел, таблица к нему, источники, оговорки.

```text
Правило: пакет — единственная содержательная единица цикла.
Правка заголовка или сниппета допускается параллельно только как
отдельный изолированный тест с собственной метрикой, не совпадающей
с основной метрикой пакета.
Доказательные элементы, необходимые пакету, входят в него и не
считаются отдельной гипотезой.
```

За цикл выбирается ровно один из двух вариантов для содержательной работы. Одновременное изменение URL, заголовка, H1, всей структуры, основного текста, внутренней перелинковки и коммерческого предложения запрещено независимо от варианта — такие изменения разносятся по разным циклам.

## 16. Контракт измерения

Обязательный документ, создаваемый до публикации и не изменяемый после неё.

### 16.1. Обязательные поля гипотезы

```md
# H-021

## Название
## Тип (изолированный тест / содержательный пакет)
## Ведущая тактика
## Что изменить
## Где изменить
## Основание (Search Console, выдача, AI Overview, конкуренты, профиль страницы)
## Ограничения при реализации

## Контракт измерения

Основная метрика:
Метрика-контекст:
Допуски по ограничителям (числовые значения, не описания):
Окно базовой линии:
Окно измерения (минимум 28 дней, если не оговорено иное):
Требование к снимку выдачи: (есть отдельный снимок кластера / только основной запрос)
Правило принятия решения: (см. таблицу 17.2)

## Статус гипотезы (PROPOSED / READY / MEASURING / DECIDED)
```

### 16.2. Подбор основной метрики по цели изменения

| Цель изменения | Основная метрика | Метрика-контекст |
|---|---|---|
| Улучшить привлекательность сниппета | доля кликов от показов | показы |
| Улучшить присутствие по запросному кластеру | показы или средняя позиция | доля кликов от показов |
| Усилить коммерческую релевантность | конверсия по кластеру | клики |
| Улучшить видимость в AI Overview | присутствие среди источников | устойчивость AI Overview |
| Устранить риск качества или достоверности | результат независимой проверки качества | отсутствие ухудшения поисковых и бизнес-метрик |

### 16.3. Пример контракта

```md
## Контракт измерения — H-021

Основная метрика:
доля кликов от показов по кластеру "миграция CRM".

Метрика-контекст:
показы по этому кластеру.

Допуски по ограничителям:
- конверсия: не ниже базовой линии более чем на 5 %;
- средняя позиция: не хуже базовой линии более чем на 1,0;
- независимая проверка качества: не хуже предыдущей версии;
- фактическая точность: 100 % новых утверждений подтверждены источником.

Окно базовой линии: 2026-08-01 — 2026-08-28.
Окно измерения: не ранее 28 дней после публикации.
Требование к снимку выдачи: есть отдельный serp-cluster-01.md.

Правило принятия решения:
принять, если основная метрика улучшилась, все ограничители в
пределах допуска и устойчивость выдачи средняя или высокая.
```

## 17. Матрица решений и уровень уверенности вывода

### 17.1. Матрица решений

| Основная метрика | Ограничители | Устойчивость выдачи | Решение |
|---|---|---|---|
| улучшилась | все в пределах допуска | средняя или высокая | принять |
| улучшилась | один ограничитель вне допуска, но некритично для цели страницы | средняя или высокая | принять с оговоркой |
| не изменилась | в пределах допуска | высокая | повторить проверку или отклонить |
| ухудшилась | любой ограничитель критически вне допуска | любая | откатить |
| любой результат | — | низкая | недостаточно данных |
| улучшилась | обнаружена фактическая ошибка или неподтверждённое утверждение | любая | откатить |

Откат не является отдельным режимом — это исход режимов «замер» или «обучение» (раздел 19).

### 17.2. Итоговый уровень уверенности вывода

Производная оценка, не требующая отдельного ручного заполнения — собирается из уже зафиксированных полей.

```text
Высокий:  окно измерения 28+ дней, устойчивость выдачи средняя или
          высокая, есть отдельный снимок кластера (если применимо),
          вариант эксперимента чистый (без смешения А и Б), все
          ограничители в допуске, в журнале искажающих факторов нет
          значимых записей.

Средний:  выполнена часть условий высокого уровня; например, окно
          измерения достаточно, но снимок кластера отсутствует,
          или в журнале искажающих факторов есть одна незначительная
          запись.

Низкий:   окно измерения короче 28 дней, либо снимок кластера
          отсутствует при заявленной зависимости от кластера,
          либо конкуренты существенно менялись в период измерения.

Недостаточный: устойчивость выдачи низкая, критичные данные
          отсутствуют, или в одном цикле смешаны изменения из
          варианта А и варианта Б.
```

Уровень уверенности не делает вывод причинным доказательством — он показывает, насколько разным экспериментам стоит придавать равный вес при формировании опыта по тактикам.

## 18. Журнал искажающих факторов

Ведётся с момента публикации до основного замера, короткий список фактов, не входящих в проверяемую гипотезу:

```md
# Журнал искажающих факторов — H-021

- 2026-09-08: competitor-02 полностью обновил страницу.
- 2026-09-14: AI Overview по основному запросу перестал отображаться.
- Изменений цены продукта, призыва к действию и состава выборки
  Search Console за период не зафиксировано.
```

Наличие значимой записи в журнале снижает итоговый уровень уверенности вывода на одну ступень независимо от показателя устойчивости выдачи.

## 19. Режимы работы

Девять режимов.

### 19.1. Приём

```text
SignalForge, приём.

Прими target.md, пять конкурентных страниц, serp-primary.md и gsc.csv.
Проверь входные материалы, определи основной запрос, регион, язык,
тип страницы и предварительный интент. Рекомендаций пока не давай.
Создай начальное состояние проекта.
```

### 19.2. Диагностика

```text
SignalForge, диагностика.

Проанализируй целевую страницу, пять конкурентов, выдачу с AI Overview
и Search Console. Обнови уровень уверенности конкурентного давления
и устойчивость выдачи. Покажи карту интентов, дефицитов,
перенасыщенных приёмов и рисков качества. Сформируй не более пяти
кандидатов на гипотезы. Страницу не переписывай.
```

### 19.3. Рекомендации

```text
SignalForge, рекомендации.

На основании диагностики и опыта по тактикам выдай максимум три
рекомендации. Для каждой укажи ведущую тактику, статус её опыта,
вариант эксперимента (изолированный или пакет), основание, основную
метрику и предварительные допуски по ограничителям.
```

### 19.4. План

```text
SignalForge, план.

Подготовь техническое задание на реализацию H-021, включая контракт
измерения. Не переписывай страницу. Опиши изменения по секциям,
сохрани подтверждённые факты и ссылки. Перечисли утверждения,
требующие проверки.
```

### 19.5. Рерайт

```text
SignalForge, рерайт.

Реализуй только H-021 в пределах согласованного варианта эксперимента.
Не меняй URL, заголовок, H1 и другие секции, если это не часть
согласованного пакета. Не добавляй цифр без источника. Покажи новую
версию изменённых блоков, различия с прошлой версией, список новых
и удалённых утверждений, список пунктов для ручной проверки.
```

Полный автоматический рерайт всей страницы запрещён по умолчанию. При необходимости — разбор на секции, список гипотез по секциям, согласование по каждой группе отдельно, затем рерайт и проверка.

### 19.6. Публикация

```text
SignalForge, публикация.

Зафиксируй target-v3.md как опубликованную версию. Контракт измерения
для H-021 закрыт и не подлежит изменению. Обнови журнал изменений
и сроки следующего измерения.
```

Публикация без оформленного контракта измерения не выполняется. До подтверждения фактической публикации статус — «готово к публикации».

### 19.7. Срез

```text
SignalForge, срез.

Вот новый serp-primary.md (и serp-cluster-01.md, если применимо)
и пять свежих конкурентных страниц. Обнови уровень уверенности
конкурентного давления, устойчивость выдачи и статус активных
гипотез. Зафиксируй новые записи в журнале искажающих факторов.
Эффект по Search Console пока не оценивай.
```

Частота — по правилу раздела 11.3.

### 19.8. Замер

```text
SignalForge, замер.

Прошло 28 дней. Вот новая выгрузка Search Console, свежие снимки
выдачи и конкурентов. Оцени только активные гипотезы по контракту
измерения. Определи итоговый уровень уверенности вывода. Новые
рекомендации пока не создавай.
```

### 19.9. Обучение

```text
SignalForge, обучение.

Обнови журнал гипотез и таблицу опыта по ведущим тактикам. Пометь
устаревший опыт. Обнови тенденцию дрейфа качества новой точкой,
включая долю необоснованного сходства. Прими решение по матрице
раздела 17. Не превращай один результат в универсальное правило.
```

## 21. Экспериментальный цикл

```text

    выдачи, конкурентов, выгрузку Search Console и состояние проекта.
2.  Диагностика — единый отчёт, включая давление конкурентов и
    устойчивость выдачи.
3.  Выбор варианта эксперимента — изолированный тест или содержательный

4.  Контракт измерения — фиксация до публикации (раздел 16).
5.  План — техническое задание по секциям.
6.  Рерайт — только согласованные секции.
7.  Проверка — Quality Guard.
8.  Публикация — фиксация версии и журнала изменений.
9.  Срезы — по правилу адаптивной частоты (раздел 11.3), с ведением
    журнала искажающих факторов.
10. Замер — по достижении окна измерения из контракта.
11. Независимая проверка качества — с указанием применённого режима.
12. Решение — по матрице раздела 17, с итоговым уровнем уверенности.
13. Обучение — обновление опыта по ведущей тактике и тенденции дрейфа
    качества.
```

```md
- Воспроизводимый вывод: для страниц типа "коммерческое сравнение"

  страницы без отдельной проверки

## H-002 — изменить заголовок

- Ведущая тактика: правка заголовка и сниппета
- Тип: изолированный тест
- Статус: недостаточно данных
- Причина: устойчивость выдачи в период измерения — низкая
- Следующая проверка: после стабилизации выдачи

# Таблица опыта по ведущим тактикам — тип страницы: коммерческое
# сравнение, интент: коммерческое сравнение вариантов

| Тактика | Позитивных | Нейтральных | Негативных | Последняя проверка | Статус |
|---|---:|---:|---:|---|---|
| закрытие содержательных дефицитов | 2 | 0 | 0 | цикл 003 | локально перспективная |

| дифференциация от конкурентов | 0 | 0 | 0 | — | не проверена |

```

Принцип журнала: нельзя записывать «таблицы работают» или «короткие тексты лучше». Нужно записывать, для какого типа страницы, интента, уровня конкурентного давления, устойчивости выдачи и итогового уровня уверенности наблюдался результат.

## 25. Модель независимых метрик

```text
Поисковые метрики: показы, клики, доля кликов от показов, средняя
  позиция, покрытие запросов.

Метрики генеративной видимости: цитирование в AI Overview,
  присутствие среди источников, позиция цитаты, совпадение ответа
  с содержанием страницы.

Метрики качества: фактическая точность, надёжность источников,
  соответствие утверждения источнику, полнота темы, читаемость,
  внутренняя согласованность, результат независимой проверки.

Бизнес-метрики: квалифицированные заявки, конверсия, доход с визита,
  число заявок на демонстрацию.
```

Одна метрика не компенсирует критическое ухудшение другой. Рост видимости при падении конверсии или обнаруженном фактическом риске не даёт решения «принять» независимо от остальных показателей.

## 27. Итоговый чек-лист SignalForge v0.4

```text
1.  Одна целевая страница, пять конкурентов, один обязательный снимок
    выдачи за цикл; дополнительные снимки подключаются автоматически
    при пакете гипотез, привязанном к отдельному кластеру.
2.  Markdown без JSON; выгрузка Search Console — в CSV или XLSX.
3.  Четыре раздельные группы метрик без единого сводного балла.
4.  Дефицит отличается от перенасыщенного приёма; зрелость контента
    конкурентов отличается от конкурентного давления оптимизации.
5.  Конкурентное давление оценивается с уровнем уверенности
    (низкая/средняя/высокая), а не бинарно; смена маршрутизации
    требует подтверждения на двух срезах или у минимум двух
    конкурентов.
6.  Приоритизация гипотез учитывает опыт ведущей тактики (в разрезе
    тип страницы × интент); статус тактики требует минимум двух
    сопоставимых исходов при приемлемой устойчивости выдачи.
7.  Каждая гипотеза с несколькими элементами получает одну ведущую
    тактику; вспомогательные элементы не получают отдельного зачёта.
8.  Опыт устаревает через три цикла, при низкой устойчивости выдачи
    в момент измерения или при смене интента страницы.
9.  Устойчивость выдачи считается по формальной балльной шкале,
    отдельно по каждому кластеру; частота срезов адаптивна.
10. Дрейф качества отслеживается как тенденция с разделением на
    обоснованное и необоснованное сходство; реакция — приостановить
    шаблонное копирование и формальное расширение, не поиск отличия.
11. Независимая проверка качества проводится в одном из трёх явных
    режимов (человек / отдельная модель / слепой чат) с обязательным
    указанием режима в отчёте.
12. Каждая гипотеза оформляется как изолированный тест или
    содержательный пакет — один вариант на содержательную работу
    цикла, без смешения.
13. Контракт измерения (основная метрика, метрика-контекст, числовые
    допуски, окно измерения, требование к снимку выдачи, правило
    решения) фиксируется до публикации и не меняется после.
14. Слово "незначительно" не используется — только числовой допуск.
15. Решение принимается по единой матрице: основная метрика ×
    ограничители × устойчивость выдачи; итоговый уровень уверенности
    вывода — производная оценка, не требующая отдельного учёта.
16. Журнал искажающих факторов ведётся с момента публикации до
    основного замера; значимая запись понижает уровень уверенности.
17. Девять режимов работы: приём, диагностика, рекомендации, план,
    рерайт, публикация, срез, замер, обучение. Откат — исход замера
    или обучения.
18. Полный автоматический рерайт запрещён без постраничного
    согласования.
19. Опыт по тактикам не переносится между проектами без пометки
    "не проверено в этом контексте".
20. Состав ведущихся документов (базовый/расширенный) определяется
    навыком автоматически по активным гипотезам и признакам риска.
```

Итоговая формула SignalForge v0.4:

```text
наблюдай среду с уровнем уверенности, а не бинарным диагнозом
→ найди подтверждённый пользовательский дефицит, отличив его
  от необоснованного сходства
→ выбери вариант эксперимента и одну ведущую тактику
→ зафиксируй контракт измерения до публикации
→ проверь источники и качество перед публикацией
→ отследи искажающие факторы во время наблюдения
→ измерь результат раздельно по поиску, генеративной видимости,
  качеству и бизнесу
→ проведи независимую проверку качества в явно указанном режиме
→ определи итоговый уровень уверенности вывода
→ обнови опыт ведущей тактики и тенденцию дрейфа качества
→ только после этого выбирай следующую гипотезу
```

Навык оптимизирует не формальные признаки страницы, а её устойчивую способность точно, полезно и доказательно отвечать на реальный запрос пользователя — и с каждым циклом точнее понимать, какие решения работают именно для этой страницы, в этом конкурентном окружении, при этой устойчивости выдачи и с какой уверенностью в выводе.
