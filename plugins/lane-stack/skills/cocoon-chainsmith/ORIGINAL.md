# COCOON CHAINSMITH v3

Мета-промпт для генерации пошаговой связки команд системы Cocoon Engine X4.
Цель — упростить работу с системой: минимальный вход, на выходе готовая,
проверенная и исполнимая последовательность команд. Промпт не стремится
охватить все теоретически возможные команды — только то, что реально нужно
для конкретной задачи.

Перед использованием прикрепите к сообщению с этим промптом все 4 скилла
Cocoon Engine X4 (CP-Navigator, Reddit Mapper Total, TGA, GIST). Без них
генератор не может проверить команды на достоверность.

---

## ВХОДНЫЕ ПЕРЕМЕННЫЕ

```yaml
GEO: ""                # страна или регион аудитории
LANGUAGE: ""            # язык аудитории и итогового контента
SITE_THEME: ""          # тематика и краткое описание сайта/продукта
SITE_URL: ""            # опционально; оставить пустым, если не требуется
TASK_TYPE: ""           # см. список ниже
TASK_DESCRIPTION: ""    # свободное описание: вводные, регуляторные ограничения,
                        # уже существующие страницы/серия/инструменты,
                        # наличие конкурентного корпуса, что уже собрано в чате
MODE: ""                # optimal | experimental
DEPTH: ""               # minimal | normal | extended
BRANCHING: ""           # нет | да | усиленное
```

Это девять переменных. Не создавайте дополнительных полей сверх них. Любые
уточнения (регуляторность темы, наличие серии статей, конкурентного
корпуса, собственных данных, уровень автономности) указывайте прямо в
`TASK_DESCRIPTION` свободным текстом — генератор обязан извлекать эти
детали из описания задачи, а не требовать отдельной анкеты.

### Справочник значений TASK_TYPE

- `создание_кокона` — построение связанной группы страниц вокруг темы с нуля
- `расширение_кокона` — добавление страниц к уже существующему кокону
- `создание_статьи` — одна страница/статья, включая продолжение серии
- `разработка_инструмента` — калькулятор, тест, симулятор, конфигуратор
- `аудит_своей_страницы` — диагностика и доработка своей страницы до кокона
- `аудит_конкурентов` — разбор чужих страниц без утверждений без корпуса
- `обновление_контента` — delta-обновление устаревшей страницы/кокона
- `реверс_инжиниринг_продукта` — восстановление workflow чужого сервиса по
  переданным материалам и поиск улучшений
- `аудит_мета_слоя` — пересборка title/description по кокону
- `аудит_compliance` — проверка регулируемой тематики на риски и обязательные блоки
- `мультиязычная_адаптация` — перенос кокона на другой язык/регион
- `аудит_заменяемости` — health-check контента на риск быть скопированным/устаревшим
- `приоритизация_пробелов` — поиск контентных пробелов и backlog
- `бриф_страницы` — только исследование и бриф без дальнейшей сборки

Формулировки нормализуются к ближайшему значению из этого списка (например,
«compliance-аудит» или «проверка соответствия» → `аудит_compliance`), а не
плодят новые категории.

### Если TASK_TYPE содержит несколько задач сразу

Например: «создать полезную статью и заодно проверить весь кокон» или
«исследовать аудиторию, спроектировать страницы и написать брифы».

```text
1. Определи primary task — то, что явно указано как конечная цель.
2. Определи secondary tasks — сопутствующие задачи.
3. Построй основной маршрут по primary task.
4. Включай secondary task в ту же связку только если она не меняет
   authority, scope и целевой уровень готовности основного маршрута.
5. При конфликте между задачами (разные владельцы результата, разный
   scope) — не смешивай их в один маршрут. Явно предложи две отдельные
   связки и укажи, с какой начать.
```

## ГЛАВНОЕ ПРАВИЛО: КОМАНДА ≠ МАРШРУТ ≠ МОДУЛЬ

**Пользовательские команды** существуют только в CP-Navigator (`/старт`,
`/кокон`, `/исследование`, `/аудит`, `/страница`, `/обновить`, `/карта-болей`,
`/язык-аудитории`, `/карта-решения`, `/карта-спроса`, `/контентные-пробелы`,
`/приоритизация`, `/проверка-источников`, `/сущности`, `/кластеры`,
`/родитель`, `/перелинковка`, `/бриф`, `/метаданные`, `/заменяемость`,
`/проверка-фактов`, `/свежесть`, `/compliance`, `/проверка-передач`,
`/проверка-готовности`, `/проверка-совместимости`, `/проверка-происхождения`,
`/проверка-scope`, `/проверка-родителя`, `/показать-собранное`, `/сохранить`,
`/сохранить-полное` и их официальные алиасы). Только их можно показывать
пользователю как «команду для ввода».

**Внутренние операции и модули** (у Reddit Mapper — `extract`, `compare`,
`detect`, `find_gaps`, `prioritize`, `generate_brief`, `delta_update` и т.д.;
у TGA — модули вида `Entity Discovery`, `Cluster Generator`, `Canonical Home
Resolver`, `SSoT Engine`; у GIST — модули A–K) не имеют собственного
слэш-интерфейса. Их нельзя превращать в придуманные команды вроде
`/reddit-extract` или `/tga-кластеры`. Они вызываются пользовательскими
командами CP-Navigator и упоминаются в пояснении к шагу как «внутренний
маршрут», а не как отдельная команда для ввода.

### Правило неизвестной команды

Если команда отсутствует в реестре приложенных скиллов, она запрещена в
`optimal`-связке даже при очевидной смысловой близости. Генератор:

```text
1. выбирает ближайшую каноническую команду CP-Navigator;
2. описывает недостающее действие через материалы: или ограничения:
   естественным языком;
3. явно указывает: «отдельной канонической команды для этого действия нет».
```

Это особенно важно для задач без одноимённой команды: `мультиязычная_адаптация`,
`реверс_инжиниринг_продукта` — они вызываются через ближайшие фасады
(`/исследование`, `/страница`, `/аудит`, `/бриф`, `/обновить`).

### Проверка перед выводом каждого шага

Для каждого шага перед выводом связки проверь:

- команда или официальный алиас найдена в приложенных скиллах;
- команда разрешена для этого действия и для указанного MODE;
- параметры команды не выдуманы;
- обязательные входы присутствуют или явно обозначены как отсутствующие;
- authority шага не нарушена (см. раздел «Кто чем владеет»);
- заявленный результат не превышает допустимый уровень готовности.

Если хотя бы один пункт не проходит — шаг не включается в `optimal`-связку
в текущем виде; он переформулируется или дополняется ограничением.

## РЕЖИМЫ (MODE)

**optimal** — только канонические команды CP-Navigator и их официальные
алиасы. Всё остальное — через `материалы:`/`ограничения:` естественным
языком. Изобретать команды или параметры запрещено.

**experimental** — разрешены только три типа расширений:

1. **веерная связка** — несколько канонических команд получают один и тот
   же корпус в одном шаге. В `optimal` каждый шаг содержит ровно одну
   команду; в `experimental` веерный шаг нумеруется внутри себя:

   ```text
   Шаг 5. Веерный анализ
   5a. /карта-болей
   5b. /язык-аудитории
   5c. /карта-решения
   ```

2. **составной запрос** — одна каноническая команда через `материалы:`
   выполняет сразу несколько действий.

3. **предлагаемый фасад** — гипотетическая, не зарегистрированная команда.
   Она **не считается исполняемым шагом основной связки**. Показывается
   только отдельным блоком «Экспериментальные варианты» после основной
   canonical-связки, с обязательной маркировкой
   `[экспериментально, не зарегистрировано]` и строкой
   `canonical fallback: /...`.

Экспериментальному режиму запрещено: присваивать статусы `resolved`,
`selected_by_gist`, `implementation_candidate`, `publication_candidate`;
обходить compliance или handoff; менять canonical parent; считать
поисковую выдачу доказательством без захвата материала.

## ГЛУБИНА (DEPTH)

- **minimal** — ориентир 6–9 шагов. Костяк: старт → регистрация материалов →
  один широкий поиск или анализ → один-два узких шага → приоритизация →
  сохранение. Целевой результат — исследование или бриф.
- **normal** — ориентир 12–17 шагов. Добавляются: язык аудитории отдельно
  от болей, критерии выбора, контрпоиск, международный/локальный срез при
  необходимости, промежуточная сверка на новые углы, бриф. Целевой
  результат — бриф или архитектурный draft.
- **extended** — ориентир 20–28 шагов. Добавляются: параллельные веерные
  связки, разбор по сегментам, научный/фактологический слой,
  compliance-проверка, сравнение периодов, сверка с уже опубликованными
  материалами серии, расширенная проверка готовности.

**Диапазон шагов — ориентир, а не обязательный заполнитель.** Не добавляй
шаги, которые не меняют результат. Если задача решается меньшим числом
шагов, укажи в начале связки: «Связка сокращена: дополнительные шаги не
добавлены, поскольку не меняют результат». Если обязательные проверки
(freshness, provenance, scope, compliance) требуют больше шагов, допустимо
превысить ориентир — с кратким объяснением причины.

### Статусы готовности принадлежат разным системам — не смешивай их

- **CP-Navigator** (aggregate outcomes): `not_started`, `hypothesis_only`,
  `candidate`, `partial`, `waiting_for_receipt`, `ready_for_review`,
  `implementation_candidate`, `publication_candidate`, `published`,
  `needs_revision`, `blocked`.
- **TGA**: `draft`, `architecture_ready`, `editorial_ready`,
  `implementation_ready`, `audit_ready`, `blocked`.
- **GIST**: `gist_not_run`, `gist_audited_candidate`, `selected_by_gist`,
  `gist_rejected`, `needs_revision`, `stale`, `gist_blocked`.

В обычном тексте связки допустима человеческая формулировка вроде «готово к
брифу» или «готово к архитектуре», но она не должна выдаваться за
канонический машинный статус чужой системы. Если связка не активировала
TGA — не используй `architecture_ready`. Наличие TGA-контекста само по себе
**не даёт** `architecture_ready`: этот статус разрешён только после
прохождения соответствующего TGA-маршрута (entity discovery, кластеризация,
canonical parent, decision traces и т.д.) и получения его отклика. Аналогично,
без GIST недостижимы `selected_by_gist` и, как следствие,
`publication_candidate` — GIST-статус `editorial_ready` относится только к
TGA-маршруту и не означает, что блоки страницы подтверждены.

## ВЕТВЛЕНИЕ (BRANCHING)

- **нет** — жёсткая последовательность без точек пересмотра. Новая находка
  не меняет существующие решения молча: она фиксируется как `unknown`,
  `blocker` или предложение к пересмотру, а фактический пересчёт выполняется
  только отдельной канонической командой (`/обновить`, `/повторить-проверку`).
  Запрещено также молча менять исходный scope задачи (тему, гео, тип
  задачи) — любое такое изменение выносится отдельным явным шагом.
- **да** — одна открытая точка перед приоритизацией/брифом: «покажи, какие
  найденные углы не укладываются в текущую структуру, прежде чем
  финализировать приоритеты». Новая ветка создаётся только после явного
  указания, какой scope и какие downstream-объекты она затрагивает.
- **усиленное** — несколько открытых точек (после широкого поиска, после
  узких анализов, перед финализацией) плюс отдельный шаг «разведка по
  неожиданным сигналам»; порядок шагов может меняться по ходу работы, если
  находка меняет приоритеты — это отмечается прямо в связке.

## ОБЯЗАТЕЛЬНОЕ НАЧАЛО

Первый шаг любой связки, независимо от TASK_TYPE, MODE, DEPTH и BRANCHING:

```text
/старт
```

`/старт` создаёт сессию, проверяет наличие приложенных документов, формирует
паспорт проекта и главное меню. Он **не заменяет** проверку совместимости.

Второй шаг — всегда:

```text
/показать-собранное
```

Фиксирует, что уже зарегистрировано в сессии, и явно перечисляет, какие
материалы из входного сообщения ещё не нормализованы и не могут считаться
доказательством, пока не пройдут регистрацию. Если материалов нет — этот же
шаг фиксирует «ранее собранные материалы не обнаружены», без пропуска шага.

Третий шаг — условный:

```text
/проверка-совместимости
```

Добавляется, если задача использует несколько скиллов одновременно
(например, требует и Reddit-исследования, и TGA-архитектуры, и GIST-страниц)
или явно зависит от конкретных версий скиллов. Для `minimal`-задач, где
используется только один-два фасада, этот шаг можно не выделять отдельно,
но если он нужен — он остаётся канонической командой, а не сворачивается в
произвольный текст.

## КОГДА ВКЛЮЧАТЬ ПОИСК (DISCOVERY)

Discovery-блок включается только в шаги, где происходит обращение к внешним
источникам (Reddit, форумы, маркетплейсы, веб-поиск, научные источники). В
шагах, которые работают только с уже зарегистрированным в сессии корпусом,
переданными пользователем материалами или предыдущими результатами связки —
discovery не включается.

```text
Режим источника: discovery.
Поиск по памяти запрещён, поисковая выдача не считается доказательством.
Для каждого источника зафиксировать статус: full (полный текст) /
excerpt (фрагмент) / metadata_only (только заголовок и ссылка) /
unavailable (недоступен).
```

## КТО ЧЕМ ВЛАДЕЕТ

CP-Navigator управляет маршрутом, scope, handoff и экспортом. Reddit Mapper
владеет доказательной базой, языком аудитории и картой спроса, но
раскрывается только через команды CP-Navigator. TGA владеет архитектурой,
canonical parent и SSoT. GIST владеет решением о содержимом страницы,
заменяемостью и метаданными. Человек может подтвердить или отклонить
решение, но не может сам присвоить странице статус `resolved` или
`selected_by_gist` — это прерогатива соответствующего модуля. Связка не
должна выдавать результат работы одного владельца как результат другого
(нельзя писать «TGA принял страницу», если передача не подтверждена
откликом — корректно: «кандидат передан в TGA, отклик не получен»).

### Scope и parent — не молчаливые изменения

Для задач, связанных с набором страниц (`создание_кокона`,
`расширение_кокона`, `аудит_своей_страницы`, `мультиязычная_адаптация`,
`обновление_контента`): связка явно фиксирует состав страниц (scope) и не
добавляет страницы в него молча — расширение scope выносится отдельным
шагом. При назначении страницы разделу проверяется один structural parent;
bridge-связь не считается вторым parent; конфликт parent блокирует
дальнейшее повышение готовности до его разрешения (`/родитель`,
при конфликте — `/проверка-родителя`).

### Финальные проверки — по условию, а не по умолчанию

Не включай все проверки во все связки. Добавляй по условию:

```text
внешний корпус или time-sensitive факты → /свежесть
handoff в TGA или GIST → /проверка-передач
claims, рекомендации, downstream-решения → /проверка-происхождения
несколько страниц в scope → /проверка-scope
назначается parent → /проверка-родителя (при конфликте)
перед итоговым сохранением → /проверка-готовности
```

## ЕСЛИ ДАННЫХ НЕ ХВАТАЕТ

| Чего не хватает | Что писать вместо утверждения |
|---|---|
| Нет реального Reddit-корпуса | Не изображать анализ Reddit; предложить план поиска |
| Нет page input для аудита | Не утверждать «блока нет»; писать «рекомендованный слой контента» |
| Нет конкурентного корпуса | Не делать заявлений о конкурентах; писать «пробел не подтверждён отсутствием у конкурента» |
| Нет отклика TGA/GIST | Писать «кандидат передан», не «принят»/«выбран» |
| Нет периодов для сравнения | Не использовать «растёт», «усиливается», «изменилось» |
| Неясна регуляторная принадлежность темы | Увеличить человеческую проверку и не делать regulated-утверждений |

---

## МИНИМАЛЬНЫЙ МАРШРУТ ДЛЯ ТОЧЕЧНЫХ ЗАДАЧ

Наличие TASK_TYPE не означает автоматический запуск полного пайплайна
Reddit → TGA → GIST. Для точечных аудитов выбирай минимально необходимый
маршрут:

- `аудит_мета_слоя` не требует Reddit-исследования — основной маршрут через
  `/метаданные`, при необходимости `/проверка-готовности`.
- `аудит_заменяемости` вызывается напрямую через `/заменяемость`, а не
  разворачивается в длинную исследовательскую связку, если пользователь не
  запросил дополнительное исследование.
- `аудит_конкурентов` без реального корпуса конкурентных страниц даёт только
  план конкурентного исследования, а не сравнение.

### Внутренний ориентир: TASK_TYPE → основной фасад (для генератора, не для обязательного вывода)

| TASK_TYPE | Основной CP-фасад | Типичный внутренний маршрут |
|---|---|---|
| `создание_кокона` | `/кокон` | исследование → архитектура TGA → страницы GIST |
| `расширение_кокона` | `/кокон` или `/обновить` | текущий scope → пробелы → parent/кластер TGA → кандидаты GIST |
| `создание_статьи` | `/страница` или `/бриф` | задача пользователя → ядро темы → карта решения → блоки-кандидаты |
| `разработка_инструмента` | `/страница` или `/бриф` | задача пользователя → модель решения → требования к инструменту → методология |
| `аудит_своей_страницы` | `/аудит` | page input → покрытие спроса → аудит GIST → аудит TGA при архитектурных изменениях |
| `аудит_конкурентов` | `/аудит` или `/исследование` | конкурентный корпус → сравнение observed → кандидатные пробелы |
| `обновление_контента` | `/обновить` | изменившиеся источники → затронутые объекты → выборочная ревалидация |
| `реверс_инжиниринг_продукта` | `/исследование` или `/страница` | переданные материалы → восстановление user flow → исследование аудитории |
| `аудит_мета_слоя` | `/метаданные` | GIST-модуль структурных полей → проверка |
| `аудит_compliance` | `/compliance` или `/аудит` | compliance CP → вертикальный baseline TGA → аудит claims GIST |
| `мультиязычная_адаптация` | `/кокон` или `/обновить` | scope/регион → язык → различия сущностей и compliance |
| `аудит_заменяемости` | `/заменяемость` | аудит заменяемости и компрессии GIST |
| `приоритизация_пробелов` | `/контентные-пробелы` → `/приоритизация` | спрос Reddit → покрытие → приоритет |
| `бриф_страницы` | `/бриф` | задача пользователя → ядро темы → карта решения → бриф-кандидат |

Эта таблица — внутренняя логика подбора маршрута, а не обязательный элемент
выходного Markdown.

## ФОРМАТ КАЖДОГО ШАГА

```markdown
### Шаг N. Название

Команда:
\`\`\`
/каноническая-команда
материалы: ...
ограничения: ...
\`\`\`

Опирается на / вызывает: [что из предыдущих шагов использует; какой
внутренний маршрут Reddit Mapper/TGA/GIST реально стоит за командой, если это
не очевидно]

Зачем этот шаг и что должно получиться: [наблюдение / гипотеза / перевод /
приоритет / бриф — и допустимый статус результата, без смешивания
словарей готовности разных систем]
```

Для шагов с риском переоценки результата (аудит конкурентов, работа без
TGA/GIST, регулируемая тема) добавляется четвёртая строка:
`Чего нельзя утверждать по итогам этого шага: ...`

## ЧТО ВЫВОДИТЬ

```markdown
# Связка команд: [краткое название задачи]

или
experimental — перечислить экспериментальные шаги и их canonical fallback
```
