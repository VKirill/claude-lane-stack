# Async / Hybrid / Synchronous режимы и req_id lifecycle

## Три режима в Яндекс XML

| Режим | Статус | Когда срабатывает |
|---|---|---|
| Synchronous | **отключен** с 1 марта 2025 | Раньше — один HTTP-запрос блокировал поток до получения SERP. Сейчас Яндекс поднял цену до 480 руб/1000, xmlstock полностью отказался. |
| Hybrid | **default** | Обычный GET без `delayed=1`. Возвращает либо SERP, либо `<error code="210">` (поставлен в очередь). |
| Async | по запросу | `&delayed=1`. Сначала возвращает `<req_id>`, потом получаешь результат отдельным GET-ом с `req_id=`. |

Яндекс Live и Google XML используют свой hybrid-режим (без `delayed=1`).

## Hybrid режим — пошагово

1. Отправляешь обычный запрос:
```
https://xmlstock.com/yandex/xml/?user=...&key=...&query=окна&lr=213
```

2. Два варианта ответа:
   - **Готовый SERP** — обрабатываешь как обычно.
   - **`<error code="210">`** — запрос принят в очередь.

3. Если 210 — **подожди 20-30 секунд** и **повтори тот же URL** (те же параметры). xmlstock запомнил задачу. Списание уже произошло при первом запросе.

4. Повторять пока не вернётся SERP или `<error code="202">`. На каждый retry — пауза 20-30 с.

**Важно**: повтор того же hybrid-запроса бесплатен (запрос уже запомнен). Списание только при первой отправке.

## Async режим — пошагово

1. Отправляешь с `delayed=1`:
```
https://xmlstock.com/yandex/xml/?user=...&key=...&query=окна&lr=213&delayed=1
```

2. Ответ:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<yandexsearch version="2.0">
  <response date="20250204T185502">
    <req_id>spr3s0ngc4citnd30muk</req_id>
  </response>
</yandexsearch>
```

3. **Persist `req_id`** (Redis / PG). Списание уже произошло.

4. Через 10-20 секунд — получение результата:
```
https://xmlstock.com/yandex/xml/?user=...&key=...&req_id=spr3s0ngc4citnd30muk
```

5. Возможные ответы:
   - **Готовый SERP** — done.
   - **`<error code="202">`** — ещё не готов, retry через 20-30 с.
   - **`<error code="201">`** — слишком частые повторные запросы из кеша (cooldown 30 с). Подожди и повтори.
   - **`<error code="203">`** — req_id истёк или не существует. Заново отправлять `delayed=1`.

## Polling cadence — критично

- **20-30 секунд** минимальный интервал между retry для одного req_id.
- **Чаще → `error 201`** ("Повторный запрос результатов (из кеша) можно совершать не чаще одного раза в 30 секунд").
- Использовать **exponential backoff с jitter**: 20 → 30 → 40 → 60 → 90 → 120 с, max 5-15 минут на одну задачу (для Яндекс XML может растягиваться от секунд до часов в зависимости от нагрузки Яндекса).
- На каждой попытке проверять, не вышло ли время хранения задачи (`error 203`).

## Double-spend trap

**Самая дорогая ошибка**: повторная отправка `delayed=1` для того же запроса без persist req_id. Каждый такой запрос — новая платная задача с новым req_id.

**Защита**:
1. Хэш ключа задачи: `sha256(engine|query|lr|domain|device|page|tbm|...)`.
2. До отправки `delayed=1` — проверять, нет ли уже активного `req_id` в хранилище.
3. После получения `req_id` — записывать в хранилище с TTL ~30 минут (время жизни задачи xmlstock).
4. Polling — только по сохранённому `req_id`.
5. После получения SERP — сохранить и пометить задачу как complete; не удалять `req_id` сразу (на случай ребута воркера → дубликат).

Пример Redis-схемы:
```
xmlstock:task:<hash>   ->  <req_id>              EX 1800
xmlstock:result:<req_id> ->  <xml-or-json blob>  EX 86400
```

## Когда какой режим использовать

| Сценарий | Режим |
|---|---|
| Один-два разовых запроса в скрипте | Hybrid (default) |
| Веб-форма "проверить позицию" с прогрессбаром | Async |
| Батч 1000-100000 запросов в воркере | Async с очередью |
| Live SERP мониторинг с дашбордом | Hybrid + кэш на стороне клиента |
| Яндекс Live, Google XML | Hybrid (async не поддерживается на этих движках) |

## Жизненный цикл req_id

```
created ──> queued at Yandex ──> processing ──> ready
   |             |                    |              |
   v             v                    v              v
delayed=1     poll: 210        poll: 202       poll: SERP
              (free)           (free)          (free)
   |
   v
spend $ ← (only here)
```

После `ready` re-fetch с тем же `req_id` снова возвращает SERP (в течение TTL). По истечении TTL — `error 203`.

## Граничные случаи

- **Очень долгое выполнение (часы)** — допустимо. Polling продолжается. xmlstock не убивает задачу досрочно.
- **Перезагрузка воркера** — поднимать с persistence req_id и продолжать polling.
- **Закончился баланс посреди очереди** — `delayed=1` вернёт `<error code="200">`. Не списывается. Существующие req_id продолжают выполняться (за них уже заплачено).
- **Ротация ключа** — req_id привязан к user, а не к key. После ротации старые req_id можно дочитать с **новым** ключом.
