# Хэлп по работе с PromptSculptor v0.4

## Что изменилось относительно v0.3

По умолчанию результат теперь приходит как **читаемый Markdown-отчёт** с сжатым промптом в текстовом блоке, а не как JSON. JSON-вывод остаётся доступен, но только если вы явно его запросите. Вся логика проверки (уровни сжатия, protected literals, dependency-проверки, forward/reverse trace, verdict) не изменилась — изменился только способ подачи результата.

## Быстрый старт

1. Откройте новый чат.
2. Прикрепите файл со спецификацией PromptSculptor v0.4.
3. Отправьте стартовый промпт (PromptSculptor-v0.4-Starter-Prompt.md) первым сообщением.
4. Дальше присылайте запросы по шаблонам ниже — по одному сценарию за раз.

## Как формулировать запрос

Минимально нужно указать:
- **mode** — COMPRESS или AUDIT;
- **текст исходного промпта** (и кандидата, если это AUDIT).

По умолчанию: **level = 2 (BALANCED)**, **output_mode = full**, **output_format = markdown**. Меняйте их только если нужно что-то конкретное — писать JSON вручную не требуется, оператор чата сам соберёт input JSON из вашего обычного текста.

### Как попросить JSON вместо markdown

JSON выдаётся только по явной просьбе. Формулировки, которые сработают:
- «дай в JSON»
- «нужен структурированный вывод, JSON»
- «output_format: json»

Формулировки, которые **не** переключат формат (и вернут markdown, как обычно):
- «сожми покомпактнее»
- «сделай короче»
- «покажи результат»

## Режим 1 — COMPRESS

### Пример A: быстрое сжатие без деталей (все дефолты → markdown, full)

```
Режим: COMPRESS.
Сожми этот промпт:

"""
Ты — ассистент службы поддержки. Всегда отвечай вежливо и по-русски.
Пожалуйста, постарайся быть полезным и давать подробные развернутые ответы,
если это возможно и уместно в контексте вопроса пользователя. Не отвечай
на вопросы, не связанные с нашим продуктом. Если не знаешь ответа, честно
скажи об этом и предложи связаться с оператором.
"""
```

Ожидаемый результат: Markdown-отчёт "PromptSculptor — Compression Report" с текстовым блоком сжатого промпта, таблицами Changes/Risks и чек-листом верификации.

### Пример B: краткий markdown-ответ без отчёта (lite)

```
Режим: COMPRESS, output_mode lite.
Сожми этот промпт:

"""
<вставьте промпт>
"""
```

Вернётся короткий блок: уровень, safe_for_deployment, сам сжатый промпт в текстовом блоке, и только high/critical риски (если есть).

### Пример C: жёсткий контроль, level 1 (GUARDED), полный отчёт

```
Режим: COMPRESS, level 1.
Это system-промпт продакшн-агента, менять логику нельзя вообще —
нужна только безопасная нормализация текста.

Промпт:
"""
<вставьте длинный system prompt>
"""
```

### Пример D: агрессивное сжатие с указанием, что можно удалять

```
Режим: COMPRESS, level 3.
removable_preferences: ["используй тёплый тон", "предлагай дополнительные примеры, если это уместно"]

Промпт:
"""
<вставьте промпт, где часть пожеланий явно необязательна>
"""
```

Без `removable_preferences` (или тегов `[OPTIONAL]` внутри самого промпта) Level 3 не станет удалять soft preferences — это осознанное ограничение, а не баг.

### Пример E: сжатие с тест-кейсами для предсказания поведения

```
Режим: COMPRESS, level 2.

test_cases:
1. Вход: "Сколько стоит доставка?" — должно быть: ответ по-русски, вежливо,
   без выдумывания цены, если её нет в контексте.
2. Вход: "Расскажи анекдот" — должно быть: отказ, т.к. вопрос не про продукт.

Промпт:
"""
<вставьте промпт>
"""
```

В отчёте появится раздел "Predicted Behavior Diff" со статусом `PREDICTED` (не `MEASURED` — это оценка модели, не реальный запуск) по каждому test case.

### Пример F: тот же запрос, но явно с JSON-выводом

```
Режим: COMPRESS, level 2, output_format json.

Промпт:
"""
<вставьте промпт>
"""
```

Вернётся JSON-объект строго по схеме `COMPRESS / JSON / FULL` — без markdown-обёртки, без пояснений вокруг.

## Режим 2 — AUDIT

### Пример G: базовая проверка "не потерялась ли логика" (markdown, full)

```
Режим: AUDIT.

Исходный промпт:
"""
<вставьте оригинал>
"""

Кандидат (сжатая версия, которую нужно проверить):
"""
<вставьте результат чужого сжатия, например из другого LLM или ручной правки>
"""
```

Ожидаемый результат: Markdown-отчёт "PromptSculptor — Audit Report" с вердиктом (PASS / PASS_WITH_WARNINGS / FAIL), таблицами Forward Trace, Reverse Trace, Protected Literal Check, Dependency Check.

### Пример H: быстрая проверка без деталей (lite)

```
Режим: AUDIT, output_mode lite.

Исходный промпт: "..."
Кандидат: "..."
```

Вернёт короткий блок: verdict, summary, критические находки — удобно для быстрой отсечки "можно деплоить / нет".

### Пример I: аудит с реальными результатами выполнения (MEASURED)

```
Режим: AUDIT.

Исходный промпт: "..."
Кандидат: "..."

test_cases:
1. id=case_1, вход: "..."

execution_results:
baseline/case_1: input_tokens=850, output_tokens=210, latency_ms=1200,
  assertion "valid JSON" = passed
candidate/case_1: input_tokens=410, output_tokens=640, latency_ms=1900,
  assertion "valid JSON" = failed
```

Раздел "Cost Assessment" покажет статус `MEASURED`, а не `ESTIMATED`, и честно отразит регресс (рост output_tokens и провал assertion) — это ровно тот случай "output explosion", о котором предупреждали исследования.

### Пример J: тот же аудит, но явно с JSON-выводом

```
Режим: AUDIT, output_format json.

Исходный промпт: "..."
Кандидат: "..."
```

Вернётся JSON-объект строго по схеме `AUDIT / JSON / FULL`.

## Как читать markdown-отчёт

- **Заголовок с уровнем** — если "Requested level" и "Effective level" разошлись, значит Cost-Aware Governor понизил уровень из-за риска. Сигнал, что исходный промпт не так просто сжать безопасно, как хотелось.
- **Раздел "Size and Cost" / "Cost Assessment"** — `UNMEASURED` означает "мы вообще не знаем реальную экономию", `ESTIMATED` — "это оценка риска, а не измерение", `MEASURED` — только если вы сами передали execution_results.
- **Verdict = FAIL** в отчёте AUDIT — что-то из hard requirements/protected literals/output contract сломано; смотрите таблицу Forward Trace на строки со статусом, отличным от PRESERVED.
- **Reverse Trace со статусом UNSUPPORTED** — кандидат добавил что-то, чего не было в источнике (частый признак "услужливого" переписывания, а не сжатия).
- **Dependency Check со статусом DANGLING** — в кандидате осталась ссылка/термин без определения, которое было удалено.
- **Таблица Risks пустая или "No risks identified"** — это ожидаемый и хороший результат, а не признак того, что проверка не сработала.

## Рекомендуемый порядок первого боевого теста

1. Возьмите один свой реальный рабочий промпт среднего размера.
2. Пример A или B (COMPRESS, level 2, markdown) — посмотрите на компрессированный текст и риски.
3. Тот же результат — через AUDIT (Пример G), сравнивая исходник и полученный сжатый текст.
4. Если AUDIT вернул PASS_WITH_WARNINGS или FAIL — посмотрите Forward Trace / Dependency Check и решите, донастраивать ли level или removable_preferences.
5. Только после стабильного PASS на level 2 переходите к level 3 (Пример D) на менее критичных промптах.
6. Если результат нужен для встраивания в код/пайплайн — повторите тот же запрос с `output_format: json` (Примеры F, J).
